# PAC思考

> **核心**: 前提(P) - 仮定(A) - 結論(C) に分解 → Aを疑う

## 仮定 ≠ 仮説

| 用語 | 定義 | 例 |
|------|------|-----|
| **仮説** | 検証対象の命題 | 「このボタンを赤くすればCVRが上がる」 |
| **仮定** | 結論と前提をつなぐ暗黙の橋 | 「ユーザーは赤を目立つと感じる」 |

**仮定は明示されないことが多い**。だからこそ、意識的に抽出する必要がある。

## PACの構造

```
P (Premise): 前提
  → 明示的に述べられている事実・条件

A (Assumption): 仮定
  → 暗黙のうちに受け入れている橋渡し

C (Conclusion): 結論
  → 前提と仮定から導かれる主張
```

**例:**

```
P（前提）: 「競合はこの機能を実装している」
A（仮定）: 「競合と同じ機能がないと負ける」← 暗黙！
C（結論）: 「我々もこの機能を実装すべき」
```

この「仮定」が正しいかどうかを検証することが重要。

## 実行プロトコル

```
1. [結論の特定]
   検証対象の結論・主張を明確にする
   例: 「マイクロサービスに分割すべき」

2. [前提の列挙]
   明示されている事実・条件を列挙する
   - 「現在のモノリスは開発速度が遅い」
   - 「チームが5つに分かれている」

3. [仮定の抽出]
   前提と結論をつなぐ暗黙の橋を探す
   - 「マイクロサービスにすれば開発速度が上がる」
   - 「チームごとにサービスを持てば独立して開発できる」

4. [仮定の検証]
   各仮定が成立するか検証する
   - 本当にそう言えるか？
   - 反例はないか？
   - 条件は何か？

5. [結論の再評価]
   仮定の検証結果を踏まえて結論を再評価
   - 仮定が崩れれば結論も見直し
   - 条件付きの結論に修正
```

## 出力テンプレート

```markdown
## PAC分析

### 結論（検証対象）
[検証する主張・結論]

### 前提（明示的事実）
1. [前提1]
2. [前提2]

### 仮定（暗黙の橋）
| # | 仮定 | 検証結果 | 備考 |
|---|------|---------|------|
| A1 | ... | [成立/不成立/条件付き] | ... |
| A2 | ... | [成立/不成立/条件付き] | ... |

### 検証詳細
#### 仮定A1の検証
- 検証方法: [どう検証したか]
- 結果: [何がわかったか]
- 判定: [成立/不成立/条件付き]

### 結論の再評価
- 元の結論: [...]
- 修正後の結論: [...（条件や制限を追加）]
```

## 併用パターン

| 併用する思考法 | 役割 |
|--------------|------|
| クリティカルシンキング | 仮定の検証を深掘り |
| アブダクション | 仮定から検証方法を導出 |
| メタ思考 | 「なぜその仮定を置いたか」を問う |

## アンチパターン

| やりがち | 問題 | 対策 |
|---------|------|------|
| 仮定を探さない | 隠れた前提に気づけない | 「なぜP→Cと言えるか」を問う |
| 仮定と仮説を混同 | 検証の焦点がずれる | 仮定＝暗黙の橋と意識 |
| 全ての仮定を疑う | 前に進めない | 影響度の高い仮定に集中 |

## 注意

**仮定は「見えない」からこそ危険**

多くの議論の齟齬は、異なる仮定を置いていることに気づいていないから起きる。PAC分解で仮定を可視化することで、建設的な議論が可能になる。
