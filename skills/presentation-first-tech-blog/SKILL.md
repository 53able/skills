# Presentation First Tech Blog

調査済みの技術材料を短いナラティブ・デッキで構造化し、スピーカーノートで説明の欠落を検出してから、単体で理解できるWeb記事へ再設計する。プレゼンテーションを記事の縮小版ではなく、物語を安価に試すプロトタイプとして扱う。

## 手順

### Step 1: 適用可否を判定する

1. 記事の目的を、問題提起、概念説明、設計判断、比較、導入判断、実測報告のいずれかへ分類する。
2. 問題から判断へ導く記事、新しい概念や設計判断を説明する記事、トークと記事を併用する企画、図解や比較を中心にする記事には、このワークフローを使う。
3. APIリファレンス、コマンド一覧、厳密なセットアップ手順、障害対応の時系列記録、網羅性を優先するチュートリアルには使わない。検索性、完全性、手順精度を優先する別の方法へ切り替える。
4. 技術材料、想定読者、公開目的が欠けている場合は、不足する項目だけを確認する。

### Step 2: 単一のワークベンチを初期化する

1. `assets/article-workbench-template.md` をコピーし、作業用Markdownを1つ作る。
2. 企画、証拠、ナラティブ・デッキ、スピーカーノート、記事本文、監査結果を同じファイルで管理する。
3. 出力先が未指定なら `outputs/<topic>-article-workbench.md` を使う。
4. 生データや実験ログは別ファイルに保存してよいが、ユーザー向けの正本はワークベンチ1つに保つ。

### Step 3: 読者と検証対象を固定する

1. 想定読者、読者の困りごと、記事が約束する変化、中心主張、中心主張を撤回または限定する条件を明文化する。
2. 中心主張を一文に圧縮する。
3. 撤回条件を書けない場合は、主張を検証可能な粒度へ狭める。
4. 読者、痛み、約束が弱い場合は、利用可能なら `tech-article-angle` を先に適用する。

### Step 4: 証拠パックを作る

1. プレゼンテーションより先に、次の材料を収集する。
   - 公式ドキュメント、仕様、論文などの一次資料
   - 実装コード、設定、API仕様
   - 実測ログ、再現手順、コマンド出力
   - 代替案との比較
   - 反例、制約、未検証範囲
2. 各主張に証拠IDを付け、ワークベンチの証拠表へ記録する。
3. 観察、外部ソースの主張、執筆者の推論を区別する。
4. 実測していない結果、出典のない数値、存在しない比較結果を作らない。
5. 根拠が不足する主張は限定するか `未検証` と記録する。
6. 最新性が関係する製品、モデル、価格、規制、ソフトウェア仕様は、執筆時点の公式資料で確認する。

### Step 5: ナラティブ・デッキを作る

1. 8〜12個を初期上限として意味のビートを並べ、内容に応じて増減する。
2. 次の順序を初期案にする。
   1. 読者が遭遇する場面
   2. 問題
   3. 一般的な説明では足りない理由
   4. 中心となる観察
   5. 証拠
   6. 提案する方法
   7. 実装または適用例
   8. 失敗条件・制約
   9. 判断基準
   10. 次の行動
3. 各ビートには、主張を一文、証拠IDまたはURL、次へ進む問いだけを記載する。
4. 1ビートに複数の独立主張がある場合は分割する。
5. 視覚装飾を作り込まず、主張の順序だけを評価する。
6. 抑制、簡潔さ、自然さの詳しい設計が必要な場合は、利用可能なら `presentation-zen-garr-reynolds` を適用する。

### Step 6: スピーカーノートで欠落を検出する

1. 各ビートに、必要な理由、前提知識、具体例、証拠の読み方、想定反論、次への接続を追加する。
2. ノートを話し言葉で記述してよいが、ブログ本文の代用品にはしない。
3. 自分の言葉で説明できない主張は、理解不足または証拠不足としてStep 4へ戻す。
4. 反論に答えられない場合は、主張を限定するか制約として明示する。

### Step 7: Web記事へ再設計する

1. `references/conversion-rules.md` を読む。
2. 中心メッセージをタイトル、導入、結論の軸へ変換する。
3. 近いビートを統合し、読者の疑問を表す見出しを作る。1ビートを機械的に1見出しへ変換しない。
4. スピーカーノートを材料として段落を書き直す。口頭の反復や話者の権威に依存する説明を除く。
5. 用語の定義、コード、実行条件、出典、代替案、例外、失敗条件、未検証範囲、図を見なくても通じる説明、再現または判断の手順を補う。
6. 各節を途中から読んでも役割が分かる構造にする。
7. Web向けの圧縮が必要なら、利用可能な場合に `readable-writing-workflow` を適用する。

### Step 8: 二方向の監査を行う

1. プレゼンテーションから記事への監査を行う。
   - ノートにしか存在しない重要な前提がないか。
   - 図がなければ理解できない説明がないか。
   - 口頭では通るが文章では飛躍する接続がないか。
   - 話者の権威だけで支える主張がないか。
2. 記事から証拠への監査を行う。
   - 主要主張の近くに根拠があるか。
   - 観察と推論を区別しているか。
   - 実測していない結果を示していないか。
   - 反証、制約、未検証範囲が消えていないか。
   - 読者が再現または判断できる情報があるか。
3. 指摘を `BLOCKER`、`MAJOR`、`MINOR` に分類する。
4. `BLOCKER` をすべて解消し、受け入れる `MAJOR` には理由を書く。
5. 修正後、古い未支持の文言が消えたことを検索または差分で確認する。

### Step 9: 決定的チェックを実行する

1. スキルディレクトリを基準に次を実行する。

```bash
python3 scripts/check-workbench.py <workbench.md>
```

2. `ERROR` が出た場合は、不足するセクションまたは必須項目を修正する。
3. `WARNING` が出た場合は、未検証事項として受け入れるか根拠を追加する。
4. コマンドが成功し、ワークベンチがディスク上に存在することを確認してから完了を報告する。
5. 検証を実行していない場合は `未検証` と明示する。

## エラーハンドリング

- 一次資料または実測根拠を取得できない場合は、断定調で完成させず `Blocked / Unverified` と記録する。
- ナラティブ・デッキが先に完成している場合は、証拠パックと撤回条件を追加して物語を再評価する。
- スピーカーノートが長文原稿になった場合は、理由、前提、具体例、証拠、反論、接続へ分解する。
- 記事がスライドの順番に依存している場合は、見出しだけを読んで論旨が分かる構造へ組み替える。
- 最新情報を確認できない場合は、該当箇所を `未検証` とする。
