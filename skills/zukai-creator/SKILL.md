# Zukai Creator

## 原則

- 一図一問を基本に、図を見た読者が何を説明できるようになるかを先に決める。
- ソースの観察と解釈を分ける。因果・順序・関連・包含を混同せず、根拠のない関係や数値を追加しない。
- 意味を担う要素は「図形1つ＋ラベル1つ」で対応づけ、同種の要素には同じ形を使う。タイトル・凡例・注釈・関係ラベルは補助テキストとして認め、無理に要素化しない。
- 矢印の方向を関係ラベルの意味に合わせる。図形・配置・文字が矛盾する図は未完成とする。
- 静的な説明図を作る。対話型HTML、等角投影、3Dは標準の制作手順に含めない。

## 手順

### Step 1: 理解の問いと図の必要性を決める

1. 媒体、目的、読者の前提知識、主メッセージを整理する。足りない情報は仮定を明記し、結論や図の構造を変える不足だけ確認する。
2. 「読者は何に答えられないか」「図を見た後に何に答えられるか」を一文ずつ書く。
3. 図が追加する説明を決める。単純な列挙には文章・表を選べる。図を明示的に求められた場合は最小限の図にする。
4. スキル同梱の `references/explanation-design.md` を読み、問い・理解のつまずき・視覚表現の方針を記録する。

### Step 2: 根拠と図の部品を対応づける

1. スキル同梱の `assets/diagram-brief-template.json` を使い、新規の図には `explanation` を含むブリーフを作る。
2. 入力の重要な記述を `source_basis` にIDとともに記録する。外部ソースならURLと該当箇所も記述に含める。
3. 要素（人、概念、処理、状態、入力、出力など）、関係、グループを抽出する。意味を担う要素にIDを付ける。
4. `claim_visual_map` で主要な主張を根拠IDと要素IDへ対応づける。矢印や注釈の意味も、対応する要素間の関係としてブリーフに残す。
5. 不明な関係は `open_questions` に記録し、確定した因果として描かない。入力が長ければ短いソース要約を添える。

### Step 3: 問いに合うパターンと形式を選ぶ

1. スキル同梱の `references/pattern-catalog.md` の選択表で、答える問い・示す関係・避ける誤読を照合する。
2. 構造が自明でなければ2候補を比べ、最も少ない解読で問いに答えられる型と採用理由を記録する。
3. 指定形式を優先する。関係・手順が中心ならMermaid、配置・注釈・空間構造が重要ならSVGを選ぶ。`explanation.output_format` は `mermaid` または `svg` にする。
4. 概要と詳細を分ける場合は各図の問いを明記する。要素数だけを理由に図を増やさず、問いに不要な線を先に削る。

### Step 4: ラフと表現規則を整える

1. 短いラベルと方向付きコネクタでラフを作る。図形・色・線・グループ化が何を意味するかを決める。
2. 関係ラベルを対象の線の近くに置き、条件分岐や省略には注釈を付ける。凡例とタイトルは要素ラベルから区別する。
3. 主なグループ表現は枠・背景色・余白などの一つを基本にする。同じ意味には同じ表現を使う。
4. 文字の太さは通常2種類までとし、色だけで状態や関係を区別しない。アイコンや装飾は構造が成立した後、理解に必要な分だけ加える。

### Step 5: ブリーフを検証して完成図を描く

1. スキル同梱の `scripts/check-diagram-brief.py` でJSONの型・必須項目・ID参照を検証する。スキルディレクトリから実行する例:

   ```bash
   python3 scripts/check-diagram-brief.py path/to/brief.json
   ```

2. エラーを修正し、警告は入力と照合して解消するか理由を記録する。構造検証の成功を、説明の正しさや描画品質の証明としない。
3. スキル同梱の `references/rendering-guide.md` に従い、実際の `.svg` または `.mmd` ファイルを作る。仕様・作図指示だけで完了扱いにしない。
4. SVGには `viewBox`、タイトル、説明を含める。Mermaidには図に対応する短い説明と代替テキストを添え、利用可能なレンダラーで表示成果物も作る。
5. 既存のプレビュー・ブラウザー・描画環境を優先し、新規依存や特定のランタイムを前提にしない。

### Step 6: 意味と描画を別々に確認する

1. スキル同梱の `references/review-checklist.md` を使い、図の主要な主張・方向・条件・包含をソースと照合する。
2. 実際に描画した図を想定表示サイズと縮小表示で見て、文字の切れ、線の交差、ラベルの取り違え、コントラストを確認する。
3. 重大な意味の誤りを先に直す。修正は最大3回を目安に、各回で意味と描画を再確認する。
4. 確認済み事項、未確認事項、残課題を記録する。未描画を確認済みにせず、重大な誤りや描画未確認が残れば「未完成」または「描画未確認」と報告する。任意の診断採点を使う場合も実点を記載し、満点になるまでの無期限反復は行わない。

## 納品

指定がなければ、次を短くまとめる。詳細なブリーフは別ファイルへ置く。

1. **完成図**: `.svg` または `.mmd` へのリンク。Mermaidは利用可能な描画成果物へのリンクも付ける。
2. **説明**: 答える問い、図種の採用理由、図の読み方を数文で記す。
3. **代替テキスト**: 見た目の列挙ではなく、主要な関係・変化・結論を文章で示す。
4. **検証結果**: ブリーフ構造、意味照合、実描画を個別に報告し、確認方法・表示サイズ・残課題を添える。

図が不要なケースは文章・表と判断理由を納品し、図用ブリーフの検証対象にはしない。

## 例外への対応

- 関係の根拠が足りなければ矢印を断定せず、要素マップと不足情報を示す。結論に必要な情報が欠ける場合は未完成とする。
- 定量比較が中心ならチャートやデータ可視化の手順へ切り替える。
- 描画環境が使えなければ構文確認できた範囲と未確認事項を明記し、ファイルを渡す。依存を勝手に追加せず、描画確認済みとは報告しない。
- 旧ブリーフは `explanation` 省略のまま検証できる。新規制作や旧図をこの手順で更新するときは説明設計を補う。
