# AIインターフェース設計

## 成果物契約

- AI機能の設計またはレビューを、観測事実、仮定、設計判断、リスク、受入条件へ分けて記録する。
- 正常系だけでなく、意図の誤解、誤出力、処理失敗、権限拒否、副作用、復旧を扱う。
- モデルの流暢さ、説明文、Chain-of-Thoughtを正しさの証拠として扱わない。
- 実施していないユーザー調査、アクセシビリティ検証、セキュリティ検証、法令適合を完了済みと記載しない。
- Markdown成果物を作る場合は、スキル同梱の `assets/ai-interface-review-template.md` の構造を使う。

## 手順

### Step 1: 対象と作業モードを固定する

1. 入力から対象製品、主要利用者、主要タスク、AIの役割、外部システム、想定成果物を抽出する。
2. 既存画面、コード、操作ログがある場合は実際に確認し、作業モードを**レビュー**にする。要件から新規に定義する場合は**設計**にする。
3. AIの役割を次から1つ以上選ぶ。
   - 提案: 情報や候補を返し、利用者が判断する。
   - 共同編集: 利用者の成果物を生成・修正する。
   - 実行: ツールを使って外部状態を変更する。
   - 自律実行: 複数工程を計画し、長時間または非同期に進める。
4. 対象、主要タスク、外部副作用の有無が不明で、設計が大きく変わる場合だけ確認質問を1件にまとめる。それ以外は仮定を明示して続行する。

### Step 2: 利用者成果とリスク階層を定義する

1. 機能一覧ではなく、利用者が達成したい結果を1文で定義する。
2. AIを使わない既存UIで十分かを確認する。検索、フォーム、フィルター、直接操作で目的を達成できる場合は、AIを補助へ限定する。
3. 各操作を次のリスク階層へ分類する。
   - R0: 読み取りのみ。外部状態を変えない。
   - R1: 局所的で即時に戻せる変更。
   - R2: 複数対象へ影響する、または条件付きで戻せる変更。
   - R3: 送信、公開、購入、削除、権限変更など重大または不可逆な操作。
4. 各階層について、自動実行、通知、計画確認、操作直前承認、実行禁止のいずれを適用するか決める。
5. リスク、可逆性、費用、処理時間、対象データが分からない操作を自動実行へ分類しない。

### Step 3: AI体験を五段階へ分解する

1. スキル同梱の `references/principles.md` を読み、対象フローを次の五段階へ分解する。
   - 構成: 接続先、記憶、権限、既定値。
   - 入力: 文脈、指示、直接操作、添付。
   - 計算: 遅延、進捗、分岐、失敗。
   - 出力: 根拠、適用範囲、編集、比較。
   - 行動: 承認、実行、監査、取消、復旧。
2. 各段階について、開始条件、表示状態、可能な操作、失敗、復旧、完了条件を記録する。
3. 状態が画面に現れない場合でも、バックエンド状態として必要なら成果物へ含める。
4. 計画、権限、承認、実行結果を一つの「処理中」状態へまとめない。

### Step 4: 能力発見と意図入力を設計する

1. AIができることと、どの程度うまくできるかを分けて記載する。
2. 対象外、不得意、参照データの範囲、更新時点、利用上限、費用を必要な時点で示す。
3. 入力を次の三経路へ分ける。
   - 暗黙の文脈: 開いている対象、選択範囲、履歴、記憶。
   - 明示的な指示: 文字または音声による依頼。
   - 直接操作: ボタン、選択、スライダー、範囲指定。
4. AIへ渡る暗黙の文脈を確認・除外できるようにする。記憶と一時文脈を区別する。
5. 頻出操作を直接操作へ置き、例外を自由入力へ残す。
6. 目的、背景、期待結果、例を入力できるテンプレートまたは段階的開示を用意する。利用者へプロンプト技術の習得を強制しない。
7. スターター例を実際の利用目的と製品能力に合わせる。汎用的なデモ文で空欄を埋めない。

### Step 5: 進捗、出力、失敗回復を設計する

1. 処理時間と作業形態に応じて進捗表示を選ぶ。
   - 短時間: 実行中であることだけを示す。
   - 複数工程: 完了工程、現在工程、次工程、阻害要因を示す。
   - 長時間・非同期: 通知、離脱、再開、承認待ちを設ける。
2. 正確に予測できない処理へ架空の進捗率を付けない。経過時間、試行回数、現在の方針を使う。
3. 出力へ次の要素を必要に応じて含める。
   - 明瞭な構造
   - 根拠と引用箇所
   - 地域、時点、版、データなどの適用範囲
   - 部分編集、比較、版の復元
   - 保存、送信、公開など次の行動
4. 下書きと送信、プレビューと公開、提案と実行を視覚的・状態的に分ける。
5. エラー時に元の入力、参照資料、途中出力、成功済み工程を保存する。
6. 再試行、入力を修正した再試行、別経路、縮退運転を区別する。
7. 外部副作用を戻せない場合は「ロールバック」と呼ばず、取消、補償操作、期限、問い合わせ経路を定義する。

### Step 6: エージェントの権限と共有制御を設計する

1. R2またはR3の作業では、実行前に目的の解釈、工程、使用ツール、対象データ、想定副作用を含む計画を示す。
2. 短時間、局所的、可逆、外部副作用なしの作業では、計画確認を省略してよい。省略理由を記録する。
3. 計画から逸脱する場合は、理由、新しい方針、影響を示し、リスクが上がる場合は再承認を求める。
4. 許可画面へ対象、操作、引数、理由、範囲、期間、回数、費用上限、承認後と拒否後の挙動を表示する。
5. 承認、編集、拒否、一時停止、中止、再開、人間への引き継ぎを必要な状態へ割り当てる。
6. 同種の低リスク操作を適切に束ね、承認疲れを減らす。R3操作を包括承認へ含めない。
7. 拒否した操作を別のツール、サブエージェント、再試行から実行しない。
8. ファイル、ネットワーク、資格情報、接続先の境界をモデル外で強制する。承認UIだけをセキュリティ境界にしない。
9. 提案、承認判断、実行、失敗、取消を追跡できる監査記録を定義する。機密データを無条件にログへ残さない。

### Step 7: 信頼、倫理、アクセシビリティを横断確認する

1. 信頼を最大化せず、利用者がAIを使う場面と疑う場面を判断できる状態を目標にする。
2. Chain-of-Thoughtや長い説明を内部推論の忠実な証拠として扱わない。計画、操作、資料、検査結果など外部から確認できる証拠を優先する。
3. 説明、信頼度、警告、AI生成ラベルを表示する場合は、利用者の判断または行動をどう変えるかを定義する。
4. データ利用、記憶、個人化、削除、異議申立て、救済、エスカレーションを設計する。
5. 影響を受ける非利用者、データ主体、脆弱な利用者を特定し、報告受付だけで救済済みとしない。
6. 次のアクセシビリティ要件を横断確認する。
   - キーボードだけで入力、承認、停止、復元まで操作できる。
   - 進捗、承認待ち、エラーを支援技術へ適切に通知する。
   - フォーカスを不意に移動しない。
   - 色、ドラッグ、音声、画像、時間制限へ代替手段を用意する。
   - 動きと逐次表示を減らせる。
7. 専門的なアクセシビリティ監査、脅威分析、法務判断が必要な場合は、対応する専門工程へ引き継ぐ。

### Step 8: 成果物を作成し、検証する

1. スキル同梱の `assets/ai-interface-review-template.md` を読み、不要な任意欄を削除して成果物を作る。
2. 設計判断ごとに、対象状態、根拠、トレードオフ、受入条件、未検証事項を記載する。
3. スキル同梱の `references/review-checklist.md` を読み、正常系、誤解系、誤出力系、副作用系、復旧系を確認する。
4. Markdown成果物を保存した場合は、スキルディレクトリを起点に次を実行する。成果物パスはその起点から指定する。

```bash
python3 scripts/validate-review.py path/to/review.md
```

5. 検証に失敗した場合はstderrに示された不足を修正し、合格するまで再実行する。
6. 最終報告では、成果物パス、実行した検証、未実施の検証、残存リスクを記載する。

## エラー処理

- 対象AIの能力、接続先、外部副作用を確認できない場合は、推定を事実として扱わず「未検証」と記録する。
- 利用者成果が定義できない場合は、画面部品を先に選ばず、主要タスクを確認する。
- R2またはR3操作の可逆性、責任者、停止条件が決まらない場合は、自動実行を禁止した暫定案を作る。
- 引用、信頼度、説明の有効性を利用者で評価していない場合は、「信頼を高めた」「過信を防いだ」と記載しない。
- サンドボックスやモデル外ポリシーを確認できない場合は、承認UIを安全性の証明にしない。
- スキル同梱の `scripts/validate-review.py` が失敗した場合は、stderrに示された見出し、未解決プレースホルダー、ローカル絶対パスを修正する。スクリプト合格をユーザビリティ、安全性、アクセシビリティの検証済み判定に使わない。
