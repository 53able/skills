# Phase 2: Decompose

> 実装スコープをタスクに分解し、依存関係とブランチ戦略を設計する

## 目標

1. 独立したタスクに分解する
2. タスク間の依存関係を特定する
3. ブランチ戦略を策定する

## 判断: 親エージェント vs サブエージェント

```
IF 単純（以下すべて該当）:
├─ 予想タスク数: 3以下
├─ 依存関係: 直線的（A→B→C）
├─ 分解の判断が明確
└─ → 親エージェントで実行

IF 複雑（以下いずれか該当）:
├─ 予想タスク数: 4以上
├─ 依存関係: 分岐あり（A→B, A→C）
├─ 分解の粒度判断が難しい
├─ 複数の分解案を比較したい
└─ → Task ツールで task-planner サブエージェントを起動（下記参照）

### サブエージェント起動: task-planner

**Task ツール呼び出しパラメータ**:

```json
{
  "subagent_type": "task-planner",
  "description": "タスク分解・ブランチ戦略設計",
  "prompt": "以下の情報からタスク分解とブランチ戦略を策定してください。\n\n【Design Docs要約】\n{Phase 1の「Design Docs要約」をここに展開}\n\n【実装スコープ】\n{Phase 1の「実装スコープ」をここに展開}\n\n【期待する出力】\n1. タスク一覧（# / タスク名 / 概要 / 見積もり / 検証方法）\n2. 依存関係グラフ（Mermaid）\n3. ブランチ戦略表（ブランチ / 親ブランチ / 対応タスク / マージ順）\n4. 整合性チェック（先行タスクと親ブランチの一致確認）\n\n【制約】\n- PR差分300行以内/タスク\n- 命名: feature/{codename}/{nn}-{modifier}（各4単語以内）\n- スタック方式: main → /00 → /01 → /02 → ...\n- 先行タスクと親ブランチは必ず一致させること\n\n【参照スキルファイル】\n.cursor/skills/task-breakdown/phases/verify.md\n.cursor/skills/task-breakdown/templates/output.md"
}
```

| 変数 | 取得元 |
|------|--------|
| `{Phase 1の「Design Docs要約」}` | explore サブエージェント出力 or 親エージェントの分析結果 |
| `{Phase 1の「実装スコープ」}` | explore サブエージェント出力 or 親エージェントの分析結果 |

> **重要**: Phase 1の出力をプロンプトに展開してから呼び出すこと。サブエージェントはコンテキストを引き継がない。

> 詳細プロンプトテンプレート: [../subagent-prompts/plan-tasks.md](../subagent-prompts/plan-tasks.md)
```

## 親エージェント実行時の手順

### Step 1: タスク分解

**分解の切り口**（3軸で検討）:

| 軸 | 説明 | 例 |
|---|-----|---|
| **機能単位** | ユーザーに価値を提供する機能ごと | 「一覧表示」「詳細表示」「編集」 |
| **レイヤー単位** | 技術レイヤーごと | 「スキーマ定義」「API実装」「UI実装」 |
| **依存関係順** | 先行タスクに依存する順序 | 「型定義→ロジック→UI」 |

**考えるべきこと**:
1. **独立性**: このタスクは他のタスクと独立してレビュー・マージできるか？
2. **サイズ**: PR差分は300行以内に収まるか？
3. **価値**: このタスクだけで何らかの価値（動作確認可能、テスト可能）を提供できるか？
4. **テスト可能性**: このタスクの完了をどう検証するか？

**出力**:
```markdown
## タスク候補リスト

| # | タスク名 | 概要 | 見積もり | 検証方法 |
|---|-----|-----|-----|-----|
| 1 | [タスク名] | [何をするか] | [S/M/L] | [どう検証するか] |
| 2 | [タスク名] | [何をするか] | [S/M/L] | [どう検証するか] |
```

### Step 2: 依存関係グラフ構築

**考えるべきこと**:
1. **先行タスク**: このタスクを開始するために、何が完了している必要があるか？
2. **後続タスク**: このタスクが完了すると、何が開始可能になるか？
3. **循環参照**: 依存関係に循環がないか？
4. **クリティカルパス**: 最長の依存チェーンはどれか？

**出力**:
```markdown
## 依存関係グラフ

### Mermaid図
graph LR
    T0[Design Docs PR] --> T1[タスク1]
    T1 --> T2[タスク2]
    T1 --> T3[タスク3]
    T2 --> T4[タスク4]
    T3 --> T4

### 依存関係表
| タスク | 先行タスク | 後続タスク |
|-----|-----|-----|
| T0 | なし | T1 |
| T1 | T0 | T2, T3 |
| T2 | T1 | T4 |
| T3 | T1 | T4 |
| T4 | T2, T3 | なし |

### クリティカルパス
T0 → T1 → T2 → T4（または T0 → T1 → T3 → T4）
```

### Step 3: ブランチ戦略設計

**命名規則**:
```
feature/{codename}/{nn}-{modifier}

例: feature/system-explain-replay/00-design-docs  ← Design Docs PR
    feature/system-explain-replay/01-schema       ← 実装タスク1
    feature/system-explain-replay/02-api          ← 実装タスク2
```

- `{codename}`: Design Docsを象徴する短い識別子（4単語以内）
- `{nn}`: 2桁のナンバリング
  - `00`: **Design Docs PR**（タスクブレイクダウン情報を含むDesign Docsの更新のみ）
  - `01`以降: 実装タスク（依存関係順）
- `{modifier}`: タスク内容を示す短い修飾語（4単語以内、ケバブケース）

**⚠️ 整合性の原則（重要）**:

> **タスクの「先行タスク」とブランチの「親ブランチ」は必ず一致させる**

| タスク | 先行タスク | ブランチ | 親ブランチ |
|--------|------------|----------|------------|
| T0 | - | `/00-design-docs` | `main` |
| T1 | T0 | `/01-xxx` | `/00-design-docs` ✅ |
| T2 | T1 | `/02-yyy` | `/01-xxx` ✅ |

❌ **アンチパターン**: 先行タスクがT1なのに親ブランチが`main`

**スタック方式（推奨）**:
```
main → /00 → /01 → /02 → /03 → ...
```

- 各ブランチは直前のブランチから分岐
- シンプルで整合性が保ちやすい

**出力**:
```markdown
## ブランチ戦略

### ブランチ定義
| ブランチ名 | 親ブランチ | 対応タスク | マージ順 |
|-----|-----|-----|-----|
| `feature/xxx/00-design-docs` | `main` | Design Docs更新 | 0 |
| `feature/xxx/01-modifier` | `/00-design-docs` | T1 | 1 |
| `feature/xxx/02-modifier` | `/01-modifier` | T2 | 2 |
```
