# Phase 3: Verify

> 生成した成果物を検証し、ユーザー承認を得る

## 目標

1. Self-refineで成果物を検証する
2. 問題があれば修正する
3. ユーザーの承認を得る

## 実行者

**必ず親エージェントで実行する**（ユーザーとの対話が必要）

## 手順

### Step 1: 検証チェックリスト

以下のチェックリストを順番に確認する:

#### 1.1 サイズの妥当性
- [ ] 各タスクのPR差分は300行以内か？
- [ ] 大きすぎるタスクは分割できないか？

#### 1.2 依存関係の妥当性
- [ ] 各タスクは依存関係順にリリースすれば単独リリース可能か？
- [ ] 依存関係に循環参照がないか？
- [ ] 依存関係が過度に複雑でないか？

#### 1.3 ブランチ戦略の整合性（⚠️ 特に重要）
- [ ] 命名規則に従っているか？
- [ ] **各タスクの「先行タスク」と「親ブランチ」が一致しているか？**
  - 例: T2の先行タスクがT1 → T2のブランチ(`/02`)の親は`/01`であるべき
- [ ] マージ順序がブランチ番号順になっているか？
- [ ] 親ブランチが`main`なのに「〇〇のマージ後に開始」という矛盾した記述がないか？

#### 1.4 MECEチェック
- [ ] タスクに漏れがないか？（全機能がカバーされているか）
- [ ] タスクに重複がないか？（同じ変更が複数タスクに含まれていないか）

### Step 2: Self-refineループ

```
検証チェック実行
    ↓
問題あり？ ─Yes→ 該当フェーズに戻って修正 → 再検証
    ↓ No
ユーザーへ提示
```

**問題発見時のアクション**:

| 問題カテゴリ | 戻り先 | 修正内容 |
|---|---|---|
| タスクサイズ過大 | Decompose Step 1 | タスクを分割 |
| 依存関係の循環 | Decompose Step 2 | 依存関係を再構築 |
| ブランチ整合性エラー | Decompose Step 3 | 親ブランチを修正 |
| スコープ漏れ | Understand Step 2 | スコープを再定義 |

### Step 3: ユーザーへ提示

検証完了後、以下の形式でユーザーに提示:

```markdown
## タスクブレイクダウン完了

### 検証結果
- サイズ妥当性: ✅
- 依存関係妥当性: ✅
- ブランチ整合性: ✅
- MECEチェック: ✅

### タスク一覧（概要）
| # | タスク名 | 見積もり | ブランチ |
|---|-----|-----|-----|
| T0 | Design Docs PR | S | `/00-design-docs` |
| T1 | [名前] | [S/M/L] | `/01-xxx` |
| T2 | [名前] | [S/M/L] | `/02-yyy` |

### 依存関係図
[Mermaid図]

### 次のアクション
1. Design Docsにタスクブレイクダウン情報を追記
2. `/00-design-docs` ブランチを作成してPR
3. 設計レビュー後、実装開始

---
この内容でよろしいですか？
修正が必要な場合はお知らせください。
```

### Step 4: ユーザー承認

- **承認された場合**: Design Docsの更新に進む
- **修正要求があった場合**: 該当フェーズに戻って修正

## 出力

承認後、[templates/output.md](../templates/output.md) の形式でDesign Docsに追記する内容を生成する。
