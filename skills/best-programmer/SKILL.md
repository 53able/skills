# Best Programmer

原則の要約と、エージェント作業への対応づけはスキル同梱の `references/principles.md` にある。

## Procedures

**Step 1: 作業の種類を判定する**
1. 依頼を次のいずれかに分類する。
   - A: デバッグ（エラー、失敗するテスト、flakyな挙動、原因不明の不具合）
   - B: 実装・設計（機能追加、修正、ツールやライブラリの導入）
   - C: 点検（自分の成果物、または他人のコード・PR・手順のレビュー）
2. 複数に当たる場合は A → B → C の順で実施する。

**Step 2: 一次資料を確定する（全種別で必須）**
1. 作業に関わるツール・ライブラリ・仕様・プロトコルを列挙する。
2. 各対象について、公式リファレンス（公式ドキュメント、標準ライブラリのドキュメント、仕様書、ソースコード、`--help`/`man`）の所在を特定し、該当箇所を読む。
3. バージョンを固定する。ロックファイルやインストール済みバージョンを確認し、そのバージョンのドキュメントを読む。
4. Q&Aサイト、ブログ、LLMの記憶は一次資料の代わりにしない。一次資料で裏付けが取れない記述は「未確認」として扱う。
5. 不慣れなツールの場合、スキル同梱の `references/principles.md` の「道具を深く知る」の4観点（歴史・現在・限界・エコシステム）のうち、作業判断に影響する観点だけを調べる。

**Step 3: 種別ごとの手順を実行する**

*A: デバッグ*
1. エラーメッセージとスタックトレースを全文読み、次を書き出す: 発生箇所（ファイル・行）、エラー種別、入力値、期待と実際の差。
2. 「たまたま」「環境のせい」「ライブラリのバグ」で片付けない。再現条件を特定するまで調査を止めない。
3. 仮説を1つずつ立て、ログ・デバッガ・最小再現コードで検証する。検証していない仮説を原因として報告しない。
4. 外部要因（OS、依存ライブラリ、ネットワーク）が原因の場合も、該当するissue・ソースコード・仕様の箇所を根拠として示す。
5. 原因が特定できない場合、調べた範囲・除外した仮説・残る仮説・次に取る観測手段を報告する。

*B: 実装・設計*
1. 仕様の曖昧な点を列挙する。コード・ドキュメントから確定できない点は推測で埋めず、利用者に質問する。質問できない状況では、置いた前提を明示して実装し、報告に含める。
2. 問題を、1つずつ動作確認できる小さな単位に分解する。各単位の完了条件（テストまたは観測可能な結果）を決めてから着手する。
3. 最も単純に動く設計を選ぶ。抽象化・汎用化・設定項目は、現時点の要件が必要とする場合だけ入れる。
4. 触ったことのないコード領域でも、読む・動かす・変更するを避けない。読んだ範囲と理解した構造を作業記録に残す。

*C: 点検*
1. スキル同梱の `assets/review-checklist.md` を読み、各項目を「適合 / 不適合 / 該当なし」で判定する。
2. 不適合ごとに、根拠（ファイル・行、ログ、ドキュメントの該当箇所）と修正案を1つずつ書く。
3. 出力はスキル同梱の `assets/review-checklist.md` の「出力形式」に従う。

**Step 4: 報告する**
1. 確認済みの事実と、未確認・推測の事項を分けて書く。
2. 知らないこと・確認できなかったことは「知らない」「未確認」と明記する。推測を書く場合は推測と明示し、その根拠を添える。
3. 参照した一次資料（URL、ファイルパス、バージョン）を列挙する。

## Error Handling
* 一次資料が存在しない、または入手できない場合: ソースコードを読む。ソースも読めない場合は、最小の実験で挙動を確かめ、その実験コードと結果を根拠として示す。
* 再現できないバグの場合: 「再現できない」で終えず、発生時のログ・環境差分・タイミング依存の有無を列挙し、再現条件を絞るための計測（ログ追加など）を提案する。
* 依頼者が推測での即答を求めた場合: 推測で答える前に、確認に必要な作業と所要時間を示す。それでも即答が必要なら、推測であることと誤りだった場合の影響を明記して答える。
* 原則同士が衝突した場合（例: 単純さと網羅的な調査）: スキル同梱の `references/principles.md` の「原則の優先順位」に従う。
