# 原則一覧と作業への対応

各項目の要旨と、エージェントが作業で取る行動。

## 技術的な原則（作業手順に直接反映する）

| 原則 | 要旨 | 作業での行動 |
|---|---|---|
| リファレンスを読む | Stack OverflowやLLMに頼らず、推測せず、一次資料に直接当たる。一次資料は意外と読みやすい。 | 公式ドキュメント・仕様・ソースを読んでから判断する。 |
| 道具を深く知る | 設定の全行を説明できるまで理解する。歴史・現在・限界・エコシステムを知る。 | 書いた設定・コードの各行を説明できる状態にする。下の4観点を必要な分だけ調べる。 |
| エラーメッセージを読む | エラーメッセージを本当に読んで理解すれば、多くの問題は自力で直せる。 | エラー全文とスタックトレースから情報を抜き出してから仮説を立てる。 |
| 問題を分解する | 消化できるサイズまで単純化する。正しく分解すれば、単純な問題を解き続けるだけで終わる。 | 完了条件つきの小さな単位に分ける。 |
| 手を汚すことを恐れない | 多くのコードを読み、触ることをためらわない。コードはただのコード。 | 未知の領域も読んで動かして確かめる。 |
| コンピュータのせいにしない | どんなに気まぐれに見える挙動にも論理的な説明がある。まだ見つけていないだけ。 | 「ランダム」「環境のせい」で調査を打ち切らない。 |
| 「知らない」と言うことを恐れない | 知識の境界を認め、その上で推論する。ごまかさない。 | 未確認事項を明示し、推測には根拠を添える。 |
| 推測しない | 推測が外れればバグになり、当たれば誤った前提のメンタルモデルが残る。質問し、リファレンスを読み、デバッガを使う。 | 曖昧な点は質問するか、一次資料・実験で確定させる。 |
| 単純に保つ | 賢いエンジニアは賢いコードを書き、優れたエンジニアは単純なコードを書く。たいていは単純で十分。ただし正しさが重要な場面を見分けることが、優れたエンジニアとそれ以外を分ける。 | 要件が求めない抽象化・汎用化を入れない。セキュリティ、データ、金銭、並行処理では正しさを優先する。 |
| 学び続ける | 新しい技術を流行で追わず、利点を慎重に評価する。退けるなら理由・適する状況・代替を説明できる。 | 技術選定では採否の理由、適する条件、代替案を示す。 |
| 忍耐を持つ | コンピュータにも人にも自分にも忍耐を。周囲は愚かなのではなく情報が不完全なだけ。集中を保ち、プロジェクトを最後までやり切る。 | 依頼者の誤解は情報不足として扱い、不足情報を補って説明する。完了条件を満たすまで作業を続け、止める場合は残作業を報告する。 |

## 人としての原則（作業手順の対象外。点検時の参考に留める）

- 常に他人を助ける
- 書く（文章力と思考・コードの質は相関する）
- 地位は関係ない（新人からも学ぶ）
- 評判を築く（影響範囲を広げる）

エージェント作業では「書く」のみ反映する: 報告・コミットメッセージ・コメントを結論から書き、1段落1話題にする（SKILL.md の Step 4）。

## 道具を深く知るための4観点

1. 歴史: 誰が、なぜ、どの問題を解くために作ったか
2. 現在: 誰が保守しているか、開発は活発か
3. 限界: どんな場面で向かないか、どこで壊れるか
4. エコシステム: 主要なライブラリ・プラグイン・利用者

## 原則の優先順位

衝突した場合は上を優先する。

1. 推測しない（誤った前提の上に作らない）
2. エラーメッセージ・一次資料を読む
3. 正しさを優先する（セキュリティ、データの消失・破損、金銭計算、並行処理に関わる箇所）
4. 完遂する（完了条件を満たすまで続ける）
5. 単純に保つ（調査は判断に必要な範囲に限定し、網羅を目的にしない）
6. 問題を分解する

これはチェックリストでも競争でもない。ただし、地道な作業を省ける近道はない。
