# 文芸的プログラミング

コードを「実行順の命令列」ではなく、「意図、根拠、実装が編み込まれた読める作品」として設計する。説明はコードの外側に後付けせず、設計判断、アルゴリズム、正当性、制約、実行可能な断片を一つの文書に配置する。

## 基本方針

- 読む順序を、コンパイラ都合ではなく人間の理解順に置く。
- 説明とコードを近接させ、片方だけが古くならない形にする。
- コメントの量を増やすだけで終わらせず、意図、判断理由、代替案、正当性を本文で扱う。
- 実行可能性を失わせない。文芸的な文書から、必要なコード断片、テスト、コマンドを取り出せる状態にする。
- 大規模な教科書化を避け、保守者が次の変更を安全に行うための物語に絞る。

## 手順

### 1. 目的と読者を固定する

1. 対象コード、対象機能、またはこれから実装するアルゴリズムを特定する。
2. 想定読者を一つに絞る。例: 将来の保守者、レビュー担当者、実装を引き継ぐ開発者、アルゴリズムを学ぶ読者。
3. 文書の成功条件を一文で書く。例: 「保守者が入力検証の設計理由を理解し、仕様変更時に安全に修正できる」。
4. 既存文書や背景説明が必要な場合だけ、`references/literate-principles.md` を読む。

### 2. 物語の骨格を作る

1. 次の順序でアウトラインを作る。
   1. 問題: 何を解くのか。
   2. 制約: 実行環境、性能、互換性、失敗条件は何か。
   3. 方針: なぜこの設計を選ぶのか。
   4. 中核概念: 重要なデータ構造、状態、関数、境界は何か。
   5. 実装断片: 説明の流れに沿ってコードを提示する。
   6. 検証: テスト、例、反例、実行コマンドを示す。
   7. 保守メモ: 変更しやすい点、壊れやすい点、未解決事項を明示する。
2. アウトラインが実行順そのものになっている場合、人間が疑問を持つ順番に並べ替える。
3. アウトラインが設計判断を含まない場合、少なくとも「なぜこの構造か」「なぜ代替案を採らないか」を追加する。

### 3. コード断片を配置する

1. 各コード断片の直前に、その断片が必要になる理由を書く。
2. コード断片の直後に、読み手が確認すべき不変条件、入力、出力、副作用を書く。
3. 断片名を付ける必要がある場合、`<<入力を正規化する>>` のように意図を表す名前を使う。
4. 断片が複数箇所から参照される場合、参照元に「この断片が満たす契約」を書く。
5. 実行可能なコードを生成する必要がある場合、`assets/literate-template.md` の形式を使う。

### 4. 説明をコードに従属させすぎない

1. 構文の逐語説明を避け、読めば分かる処理は短くする。
2. 代わりに、通常のコメントに入りにくい情報を本文に置く。
   - アルゴリズムの意図
   - 正当性の根拠
   - 設計上の決定理由
   - 失敗例と境界条件
   - 性能やメモリ使用量の見積もり
   - 変更時に守るべき不変条件
3. 読者が疑問に思わない情報を削る。
4. 読者が推測するしかない前提を明示する。

### 5. 検証可能性を組み込む

1. 文書内に少なくとも一つの実行例、テスト、または検証コマンドを含める。
2. 実行結果が未確認の場合、結果を事実として書かず `未実行` または `TODO: run` と明示する。
3. Markdown 形式の文芸的プログラムを作成・レビューする場合、次を実行して構造を点検する。

   ```bash
   python scripts/check-literate-markdown.py path/to/document.md
   ```

4. スクリプトの警告は機械的な目安として扱い、文脈上必要な例外は本文で説明する。

### 6. 最終レビューを行う

1. `references/review-checklist.md` を読み、文書またはリファクタ案を点検する。
2. コードと説明のどちらか一方だけが更新される危険箇所を探す。
3. 「物語として読めるが、実行可能性が曖昧」な箇所を修正する。
4. 「実行可能だが、意図が読めない」箇所を修正する。
5. 最終出力に、未検証事項、実行した検証、残る保守リスクを短く添える。

## 出力形式

- 新規文芸的プログラムを作る場合: Markdown 文書、コード断片、実行方法、検証方法を含める。
- 既存コードを文芸的に再構成する場合: 変更前の読みにくさ、再構成後の章立て、対応するコード断片、移行リスクを示す。
- レビューの場合: 強い点、意図が欠ける箇所、説明とコードの乖離、保守時の危険箇所、改善案を示す。

## Error Handling

- 対象コードが存在しない場合、実装を推測せず、文書の骨格と未確認の実装プレースホルダーだけを作る。
- 対象言語やビルド手順が不明な場合、実行可能性を `未検証` と明示し、必要な確認質問またはコマンド候補を書く。
- 文書が長くなりすぎる場合、背景理論を `references/` に分離し、本文は保守判断に必要な説明へ圧縮する。
- 単なるコメント追加の依頼に見える場合、文芸的プログラミングが必要かを判断し、通常のコメント改善で足りるならこのスキルを使わない。
