# タスク別モデル・オーケストレーター

親エージェントがタスクを判定し、Agent ツールの呼び出しごとに `model` を指定して結果を検証する。モデルを自動的に切り替えるプログラムではなく、モデル別の一律分業を品質保証として扱わない。

## 手順

**Step 1: 委譲の必要性と制約を確認する**

1. 依頼の目的、受入条件、許可された編集対象、禁止操作、利用可能なテスト、予算または呼び出し上限を抽出する。不明な高影響操作は実行せず確認する。
2. 一回で終わる小さな作業、または委譲準備のほうが高くつく作業は親が直接処理する。複数の独立した探索、局所的な実装、レビューでのみ委譲を検討する。
3. 実際に利用できるモデル、Agent ツールの `model` 指定、許可されたサブエージェント、課金方式を確認する。モデルの利用可否や価格を推測しない。サブスクリプションではトークン推計を請求額と呼ばない。
4. 既存のプロジェクト指示、権限、承認を維持する。スキルの発動は追加権限を与えない。

**Step 2: 作業単位を分類して割り当てる**

1. 依頼を、入力・期待出力・検証方法を持つ独立した作業単位に分解する。曖昧さ、必要な途中判断、誤りの影響、可逆性、外部オラクルの有無を作業単位ごとに記す。
2. スキル同梱の `references/routing-policy.md` を読み、各作業単位について委譲不要、Haiku、Sonnet、Opus、または人間確認を選ぶ。価格だけで選ばない。迷う場合は Sonnet で限定的に調査し、確証のない変更は実行しない。
3. 安価なモデルの担当は、狭い入力・明瞭な完了条件・独立した検証・安全な再試行を満たすものに限定する。実行中の設計判断や障害対応が難しければ実行担当も Sonnet または Opus にする。
4. 並列化はファイル競合・共有状態のない作業だけに限定する。編集対象が重なる場合は逐次実行する。探索だけなら読み取り専用の Explore 等を優先するが、組み込み Explore のモデルを Haiku と決めつけない。

**Step 3: 有界な委譲を実行する**

1. スキル同梱の `assets/delegation-packet.md` の構造を使い、目的、対象範囲、禁止事項、入力、検証コマンドまたは観測方法、完了報告、停止条件、最大試行回数を一つの委譲メッセージに記す。
2. Agent ツールで、使用する subagent type と呼び出し単位の `model: haiku`、`model: sonnet`、または `model: opus` を明示する。呼び出し側にこの指定が見えない場合は黙って代替しない。既存のカスタム subagent の `model` 設定と環境変数を確認し、実行モデルを `/tasks` 等で確認する。確認できなければモデル選択を未検証と報告する。
3. サブエージェントに無制限の再帰委譲、無制限の再試行、勝手なスコープ拡大を許さない。必要な結果が揃ったら追加の Agent 呼び出しをせず、結果を返す。外部送信、公開、削除、本番変更は既存の人間承認ゲートへ戻す。

**Step 4: 外部証拠で合否を判定する**

1. 子の「完了」「自信がある」という報告を合格判定に使わない。差分を確認し、委譲前に指定したテスト、型検査、静的解析、再現手順、または人間レビューで検証する。検証器の対象外の要件は未検証と記す。
2. 合格なら親が要件と副作用を確認して統合する。検証器が弱い場合は安価モデルの合格結果も標本監査し、誤受理を見落とさない。
3. 不合格で原因が局所的・検証可能なら、エラーログを添えて同じ担当へ最大1回再試行する。同じ失敗、曖昧な原因、設計変更の必要、重大な副作用は上位モデルへ昇格する。昇格先には元の目標、差分、検証失敗、試行履歴を渡し、最初から同じ調査を繰り返させない。
4. 上位モデルでも合格しない、検証不能、予算超過、権限外の場合は停止し、人間へ状況と残る選択肢を返す。検証のない自己反省の反復をしない。

**Step 5: 品質と費用を振り返る**

1. スキル同梱の `assets/run-summary.md` の構造を使い、実行モデル、実際の試行回数、外部検証の結果、昇格理由、使用量または課金額が取得できた範囲、人的修正、残存リスクを報告する。未取得は「未取得」と書く。
2. 同種の仕事が反復する場合だけ、スキル同梱の `references/evaluation.md` の最小比較を実施する。まず直接実行とルーティングを同じ受入基準で比べる。最適配置や節約率を実測なしで宣言しない。

## エラーハンドリング

- Agent ツールがない、モデル指定が使えない、または指定モデルが許可されていない場合は、別モデルで実行したと偽らず、親が実行するか設定変更を依頼する。
- モデルの実行時代替や環境変数による強制が見つかった場合は、実際のモデルを記録し、予定の費用比較からその試行を除く。
- 読み取り専用の依頼では計画ファイルを含めて書き込まず、確認した結果だけ返す。書き込み不可の環境で Write を試さない。
- テストがない場合は、先に最小の観測可能な受入条件を定める。誤りの影響が大きければ人間の承認前に変更を適用しない。
- 料金情報や使用量が得られない場合は、コスト優位を主張しない。時間、試行回数、受入結果を別々に報告する。
