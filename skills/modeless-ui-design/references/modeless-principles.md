# モードレスUI設計の判断基準

この資料は、モードレス化の判断が必要なときだけ読む。

## 定義

- **モードレス**: 特定タスクの完了やキャンセルを強制されず、ほかの対象の参照または操作を続けられる状態。
- **モーダル**: 特定タスクを完了または中止するまで、ほかの操作が制限される状態。
- **モード**: 同じ入力が状態によって異なる結果を生む、または現在状態を覚えておく必要がある操作状態。

コンポーネント名とモダリティを混同しない。Dialog、Drawer、BottomSheet、Popoverは、実装によってモーダルにもモードレスにもなる。

## 原則

1. **作業の連続性を保つ**
   現在の操作中も、必要な背景情報の参照と別操作への移動を可能にする。

2. **記憶すべき状態を減らす**
   閲覧・編集・保存待ちなどの明示的なモード遷移を減らす。自動保存やインライン編集を検討する。

3. **小さく可逆な操作はその場で完了させる**
   軽微な操作を確認ダイアログで中断しない。直接操作とUndoを優先する。

4. **複雑なモーダルはタスク分解から見直す**
   複数タスクを一つのモーダルへ詰め込まず、情報設計と操作単位を再検討する。

5. **長い処理を待機モードにしない**
   バックグラウンド処理、進捗表示、再試行、キャンセルを設計する。安全に戻せる場合だけ楽観的更新を使う。

6. **主対象と補助情報を同時に見せる**
   背景情報が必要な場合は、画面を覆うより並置を優先する。

7. **名詞から動詞へ進む**
   先に対象オブジェクトを選び、その対象に可能な操作を提示する。

8. **フィードバックは返すが操作を止めない**
   成功はトーストやインライン表示で伝える。重要な失敗や対応必須状態は永続的に残す。

9. **モーダルは必要な拘束に限定する**
   不可逆、高損失、必須同意、整合性維持、独立した集中作業など、拘束する理由を明示する。

10. **運用でモードを増やさない**
    機能追加のたびにモーダルや確認画面を足さず、既存オブジェクトとアクションへ統合できるか確認する。

## 判断マトリクス

| 条件 | モードレスを優先 | モーダルを候補 |
|---|---|---|
| 影響 | 軽微 | 重大 |
| 可逆性 | すぐ戻せる | 戻せない |
| 頻度 | 反復的 | 例外的 |
| 背景参照 | 必要 | 不要 |
| 並行作業 | 可能 | 禁止する必要がある |
| 必須性 | 任意 | 飛ばせない |
| 処理時間 | バックグラウンド化できる | 排他的な完了が必要 |

一つの軸だけで決めない。不可逆性と影響度を最優先し、参照継続、頻度、処理時間を組み合わせて判断する。

## モードレス化パターン

| 問題 | 候補パターン | 必須の安全策 |
|---|---|---|
| 軽微な削除確認 | 直接削除 + Undo | Undo期限と復元結果を表示する |
| 編集画面への遷移 | インライン編集 / 常時編集 | 自動保存状態と競合を表示する |
| 保存待ち | 非同期保存 | 失敗、再試行、未保存状態を残す |
| 補助情報の参照 | サイドパネル / BottomSheet | 主対象の参照・操作を維持する |
| 成功通知 | トースト / インライン表示 | 操作結果を識別可能にする |
| 長時間処理 | バックグラウンドジョブ | 進捗、キャンセル、完了通知を用意する |

## モーダルを維持する代表条件

- 完了後に取り消せず、損失が大きい。
- 同意や確認を飛ばすと法的・安全上の要件を満たさない。
- 背景操作との同時実行でデータ不整合が起きる。
- 主作業から独立した複雑な入力に集中する必要がある。
- ユーザーが明示的に中断を選び、復帰地点が保証される。

広告や一般的なお知らせを「必ず見せたい」という提供者都合だけでモーダル化しない。

## 適用上の注意

この判断基準だけで、ユーザビリティ、アクセシビリティ、法令適合、実装可能性を保証しない。必要に応じて専門レビューと実機検証を追加する。
