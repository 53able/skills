# モードレスUI設計

## 手順

**Step 1: 設計対象と成果物を固定する**
1. 入力から対象画面、主要ユーザー、達成したい目的、主要オブジェクト、現在の操作フローを抽出する。
2. 入力が既存UIの場合は「レビュー」、新規要件の場合は「設計仕様」を成果物種別として選ぶ。
3. 画面、コード、操作ログを実際に確認していない場合は、観測済みの事実と推定を分ける。未観測の挙動を断定しない。
4. 重大性、可逆性、処理時間、参照継続の必要性が不明な場合は、仮定を明記して暫定案を作る。判断を左右する不足情報だけを質問する。

**Step 2: 現在のモードと中断点を列挙する**
1. ユーザーフローを開始条件、操作、状態変化、完了条件、失敗、復旧に分解する。
2. モーダル、全画面遷移、待機画面、編集モード、確認ダイアログ、入力ロックをモード候補として列挙する。
3. 各候補について、次の観測可能な制約を記録する。
   - 背景を参照できるか
   - 背景を操作できるか
   - 別の作業へ移れるか
   - 現在の状態を記憶させるか
   - 完了またはキャンセルを強制するか
4. コンポーネント名だけで分類しない。Drawer、BottomSheet、Popover、Dialogのいずれも、背景操作を拘束するならモーダルとして扱う。

**Step 3: モードレス化の適否を判定する**
1. 判断時にスキル同梱の `references/modeless-principles.md` を読む。
2. 各操作を次の軸で評価する。
   - 影響度: 軽微 / 中程度 / 重大
   - 可逆性: 即時に戻せる / 条件付きで戻せる / 戻せない
   - 参照継続: 背景情報が必要 / あると便利 / 不要
   - 処理時間: 即時 / 短時間 / 長時間
   - 必須性: 任意 / 推奨 / 飛ばせない
   - 作業独立性: 主作業の一部 / 並行可能 / 独立して集中が必要
3. 軽微、可逆、反復的、参照継続が必要な操作はモードレスを優先する。
4. 重大、不可逆、飛ばせない、または独立した集中が必要な操作はモーダルを候補にする。
5. 「見せたい」「注目させたい」だけをモーダル採用理由にしない。ユーザーの操作を拘束する必要性を説明できない場合はモードレス案を優先する。

**Step 4: モードレスな操作へ再構成する**
1. 複雑なモーダルを見つけた場合は、UI部品を置き換える前に、混在するタスクとアクションを分解する。
2. 主要オブジェクトを特定し、「名詞を選ぶ → 動詞を選ぶ」の順に操作を並べる。
3. 小さく可逆な操作は、インライン操作、直接操作、自動保存、Undoへ置き換える。
4. 背景参照が必要な操作は、サイドパネル、非モーダルDrawer、BottomSheet、Popover、フローティングパネルを候補にする。
5. 長時間処理はバックグラウンドへ移し、進捗、完了、失敗、再試行、キャンセルの状態を設計する。
6. 成功通知はトーストまたはインライン表示を候補にする。重要な失敗やユーザー対応が必要な状態を、一時表示だけで済ませない。
7. 楽観的更新を使う場合は、失敗時のロールバック、競合、重複実行、接続断からの復旧を定義する。

**Step 5: モーダルを残す場合の根拠を記録する**
1. モーダルを残す各操作について、次のいずれが成立するか記録する。
   - 取り消せない、または損失が大きい
   - 法的・安全上・システム上、完了前に先へ進めない
   - 独立した複雑な作業へ集中させる必要がある
   - 背景操作との同時実行がデータ不整合を生む
2. モーダルを閉じる方法、キャンセル時のデータ保持、再開方法、フォーカスの戻り先を定義する。
3. 重大操作では、対象、影響、実行結果を具体的に表示する。「本当によろしいですか」だけの確認文を避ける。

**Step 6: 状態と例外を仕様化する**
1. 初期、編集中、保存中、成功、失敗、オフライン、競合、権限不足、部分完了の状態を必要に応じて定義する。
2. 各状態で可能な操作、禁止する操作、表示するフィードバック、復旧手段を記録する。
3. キーボード操作、フォーカス順、スクリーンリーダー通知、縮小画面での表示を実装要件として列挙する。ただし、専門的なアクセシビリティ適合を未検証のまま宣言しない。
4. モバイルではデスクトップ案を縮小するだけにせず、主対象、補助情報、操作の優先順位を再設計する。

**Step 7: 成果物を作成する**
1. スキル同梱の `assets/modeless-ui-review-template.md` の構造をコピーする。
2. 観測事実、設計判断、根拠、未検証事項を混ぜずに記載する。
3. 改善案ごとに、変更前、変更後、採用理由、トレードオフ、受入条件を記載する。
4. 具体的なコンポーネント名より先に、守るべき振る舞いを記載する。
5. 実装していない挙動、実施していないユーザーテスト、確認していないアクセシビリティ要件を、完了済みとして扱わない。

**Step 8: 成果物を検証する**
1. 次の最小オラクルを確認する。
   - 主作業を中断せずに対象操作を完了できる
   - 重要な失敗が一時通知だけで消えない
   - 不可逆操作が誤って軽量化されていない
   - 非同期処理の失敗と再試行が定義されている
   - モーダルを残す理由が操作拘束の必要性として説明されている
2. Markdown成果物を保存した場合は、スキルディレクトリを起点に `python3 scripts/validate-review.py <成果物パス>` を実行する。
3. 検証に失敗した場合は不足セクションを補い、再実行する。

## エラー処理

- 入力が画面名やコンポーネント名だけの場合は、モードレス化を断定せず、主要オブジェクト、操作目的、可逆性、失敗時の影響を確認する。
- 背景操作の可否を観測できない場合は「未検証」と記録し、コード、動作環境、画面録画のいずれかを要求する。
- モーダルを廃止するとデータ破壊、法的同意の欠落、安全上の問題が起きる場合は、モードレス化を中止してモーダル案と安全要件を維持する。
- 楽観的更新の整合性戦略を定義できない場合は、非同期化だけを採用し、楽観的更新を採用しない。
- スキル同梱の `scripts/validate-review.py` が失敗した場合は、stderrに示された見出しを追加する。検証スクリプトの合格を設計内容の妥当性やユーザビリティ検証の代替にしない。
