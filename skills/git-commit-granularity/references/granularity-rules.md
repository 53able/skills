# コミット粒度の判断ルール

## アトミックコミットの定義

1つのコミットは「単一のアトミックなチェンジセット」でなければならない。

| 原則 | 説明 |
|------|------|
| Single-concept | バグ修正・機能追加・リファクタリングを混ぜない |
| Semantic-gap-free | コードが壊れる中間状態を履歴に残さない |
| Always-buildable | 各コミット時点でビルド・テストが通過する |
| Logical-sequence | 大きな変更は独立して成立する単位のシーケンスへ分割する |
| Clean-history | Push 前に冗長な中間コミットをまとめる |

## セマンティックギャップ判定フロー

```
変更に「削除」と「追加」が含まれるか？
        │
    YES ─┤
        │  削除と追加は同一ファイルの変更か？
        │         │
        │      NO ─┤  （別ファイルへの移動など）
        │         │   → 削除と追加を同一コミットへ含める ✅
        │         │
        │      YES ─┤  （同一ファイル内の変更）
        │            └─ 通常の変更として扱う ✅
        │
    NO ─┴─ セマンティックギャップのリスクなし ✅
```

## Conventional Commits type 判定フロー

```
変更の主な目的は？
├─ バグを直す                → fix
├─ 新しい機能を追加する        → feat
├─ 振る舞いを変えずに整理する  → refactor
├─ テストのみ追加・修正        → test
├─ ドキュメントのみ            → docs
├─ フォーマット・タイポ        → style
├─ ビルド・CI・依存変更        → chore / build / ci
└─ パフォーマンス改善          → perf
```

## コミット分割の判断基準

### 分割すべきケース
- 1つのコミットで複数の目的（バグ修正 + 機能追加）が混在している
- コミットメッセージが「〜と〜を修正」のように `and` で繋がる
- `git diff --stat` の変更ファイル数が 10 を超え、かつ内容が無関係

### まとめるべきケース
- 関数の移動（削除 + 追加のペア）
- 機能追加とその直接的なテスト追加
- リネームとそのリネームを使うすべての参照変更
