# プロジェクト要件管理

## 手順

**Step 1: 依頼と意思決定境界を確定する。**

1. 依頼文、既存の計画、仕様、課題、利用者調査を確認する。
2. 不足する情報を、解決すべき事業課題、期待成果、対象利用者、制約、期限、既知の不確実性に分ける。
3. 要求と決定を混同しない。決定権者が未特定なら、実装・優先順位・ベースラインの確定を停止し、決定権者の特定を要求する。
4. 実装案が先に提示されている場合も、先にその案が解く事業課題と成功条件を確認する。

**Step 2: 要件ワークブックを作成する。**

1. スキル同梱の `assets/requirements-workbook-template.md` を複製して、プロジェクトの要件ワークブックを作成する。
2. 課題を原因・影響・根拠・未確認事項に分けて記録する。
3. 事業目標を、観測方法、測定時点、目標値または判定基準、責任者とともに定義する。
4. 対象範囲と非対象範囲を記録する。境界を越える外部システム、手作業、組織プロセス、データ移行も列挙する。
5. ステークホルダーを役割、関心、提供できる知識、決定権、関与時期で整理する。

**Step 3: 要求を引き出し、分析する。**

1. 利用者の目標、作業、起点となるイベント、通常経路、例外、期待結果を確認する。
2. 機能要求、品質属性、データ要求、外部インターフェース、業務ルール、制約を別々に記録する。
3. 各要求を、事業目標または利用者目標へ関連付ける。関連付けられない要求は、保留または除外候補として扱う。
4. 曖昧語、未定義の用語、暗黙の前提、相反する要求、実現性不明の要求を未解決事項として分離する。
5. 複雑な流れ、条件分岐、状態、データ関係、外部連携がある場合は、文章だけで確定しない。適切なプロセス図、状態遷移、決定表、コンテキスト図、データモデル、プロトタイプのいずれかを作成する。
6. 品質属性は「速い」「安全」「使いやすい」で終わらせない。対象、条件、測定方法、許容基準を記録する。

**Step 4: 仕様と受入条件を整える。**

1. 成果物を新規作成またはレビューする前に、スキル同梱の `references/deliverable-rules.md` を読み、必要な情報単位を確認する。
2. 要求を一意の識別子、短い名称、根拠、優先度、状態、所有者とともに記録する。
3. 各要求を、単一の振る舞いまたは検証可能な条件として表現する。
4. 受入条件を、前提、操作またはイベント、期待結果で記述する。必要なら Given–When–Then 形式を使う。
5. 例外、境界値、失敗時の振る舞い、権限、データ不整合、外部依存の失敗を受入条件または未解決事項に含める。
6. 用語の揺れを防ぐため、重要語を用語集に追加する。
7. 要件ワークブックを保存した後、`python3 scripts/validate-deliverable.py requirements <path>` を実行する。失敗した場合は、表示された不足見出しまたは空欄を修正して再実行する。

**Step 5: 優先順位とベースラインを合意する。**

1. 優先順位を、事業価値、緊急性、リスク低減、依存関係、実装・検証コスト、学習価値で比較する。
2. 優先順位の根拠と、先送りによる影響を記録する。
3. 時間固定なら、チームの実装・検証能力が満たされるまで高優先度要求を入れる。範囲固定なら、論理的にまとまった要求群を選び、見積もりと日程の調整を行う。
4. ベースライン候補に、対象要求、除外要求、前提、依存関係、受入条件、決定権者、承認期限を含める。
5. 承認済みのベースラインだけを実装対象として扱う。未承認の要求は、提案または変更要求として分離する。
6. スキル同梱の `assets/baseline-template.md` を複製してベースラインを記録し、`python3 scripts/validate-deliverable.py baseline <path>` を実行する。

**Step 6: 要求を検証する。**

1. 利用者代表、業務専門家、設計者、開発者、テスト担当者を、知識と影響範囲に応じてレビューへ参加させる。
2. レビューで、正しさ、完全性、一貫性、実現可能性、優先順位、検証可能性、用語の統一、例外処理を確認する。
3. 要求から受入テストを導出し、要求・モデル・テストの不一致を修正する。
4. 高リスクまたは不確実性の高い要求は、実装前にプロトタイプ、実験、利用者確認のいずれかで検証する。
5. 検証結果を、承認、修正要、保留、却下に分けて記録する。承認と妥当性確認を同一視しない。

**Step 7: 変更を管理する。**

1. ベースライン後の追加・修正・削除は、すべて変更要求として登録する。
2. スキル同梱の `assets/change-request-template.md` を複製して、変更理由、対象ベースライン、影響範囲、選択肢、見積もり、優先度、リスク、決定を記録する。
3. 変更の事業目標への寄与、要求・設計・テスト・データ・運用・日程への影響、依存関係、トレードオフを評価する。
4. 決定権者が承認、却下、保留、次ベースラインへの移送のいずれかを選択するまで、変更を実装対象へ混入させない。
5. 承認済みの変更は、要求、関連モデル、受入条件、テスト、ベースラインを更新し、影響を受ける関係者へ通知する。
6. `python3 scripts/validate-deliverable.py change <path>` を実行する。

## 判断規則

- 要求の詳細度は、誤解・手戻り・失敗のリスクに応じて増やす。近接して会話できる小規模チームと、外注・分散・規制対象の案件を同じ粒度で扱わない。
- 要求は一回で完成させず、引き出し、分析、仕様化、検証を反復する。
- ベースラインは変更禁止ではない。変更の影響とトレードオフを可視化して、次の合意済み状態へ更新する仕組みとして扱う。
- 承認者が不在、成功条件が不明、対象範囲が未定、受入条件が検証不能のいずれかなら、実装開始を推奨しない。

## エラー処理

- 決定権者が不明な場合は、要求を確定しない。決定すべき事項、候補者、決定期限を未解決事項として記録する。
- ステークホルダー間で要求が競合する場合は、両方の要求を統合して曖昧にしない。競合、影響、選択肢、判断基準を記録し、決定権者へエスカレーションする。
- ベースライン後に緊急変更が必要な場合は、変更評価を省略しない。評価を最小化しても、対象、理由、影響、決定者、更新したベースラインを記録する。
- `scripts/validate-deliverable.py` が失敗した場合は、標準エラーに示された見出しまたは空欄を修正してから再実行する。
