# ケース行列の設計

必要になったときだけ本ファイルを読む。

## 1. 主張を軸へ分解する

次の軸から、主張に関係するものだけを選ぶ。

| 軸 | 代表ケース |
|---|---|
| 正常系 | 最小入力、代表入力、最大想定入力 |
| 負例 | 対象機能を使わない、似た語を含むだけ、既に満たす |
| 境界 | 空、null、0、1、上限直前、上限、上限超過 |
| 障害 | 4xx、5xx、切断、遅延、破損応答、部分応答 |
| 時間 | タイムアウト、再試行、バックオフ、長時間実行 |
| 構成 | 既定値、明示値、無効値、欠損値、競合値 |
| 互換性 | 最小対応版、現行版、次期版、arm64、amd64/Rosetta |
| 資源 | CPU制限、メモリ制限、ディスク不足、同時実行 |
| 状態 | 初回、ウォーム、再開、重複実行、途中失敗後 |
| セキュリティ | ネットワークなし、読み取り専用、権限不足、秘密の非出力 |

全組合せを機械的に作らない。単一軸ケースを先に作り、重要な交互作用だけをペアワイズで追加する。

## 2. 3群を必ず分ける

- **target**: 主張が成立すると期待するケース。
- **boundary/failure**: 成否の境界または故障時のケース。
- **negative/unrelated**: 対象外を誤検知しないことを確かめるケース。

分類器、レビュールール、エージェント挙動では、targetだけを増やさない。偽陽性を測る負例と、語彙は似るが意味が違う境界例を同数程度用意する。

## 3. ケース数を増やす判断

次のいずれかを満たす場合だけ追加する。

1. 新しい失敗モードを覆う。
2. 既存オラクルの偽陽性または偽陰性を検出できる。
3. バージョン、構成、資源の交互作用を検証する。
4. 非決定性を推定する反復になる。
5. 実利用で頻度または影響が高い。

ラベル、説明、ファイル名だけを変えた同値ケースは増やさない。

## 4. オラクルを先に定義する

優先順位:

1. 終了コードと機械可読な出力。
2. 生成物の存在、内容、ハッシュ。
3. 明示したstdout/stderr文字列。
4. 時間、資源、回数の測定。
5. 人手観察。

人手観察だけのケースは自動PASSにしない。`UNVERIFIED` としてレポートへ分離する。各ケースではオラクル成立時の仮説との関係を `support`、`falsify`、`neutral` で事前登録する。オラクル成立は期待観察との一致であり、常に仮説支持を意味するわけではない。

- `support`: オラクル成立が仮説の支持証拠になる。期待した全supportケースと全反復が欠損なく成立し、期待した全falsifyケースと全反復が判定済みで棄却条件を観察しなかった場合だけ支持判定に使う。
- `falsify`: オラクル成立が事前登録した棄却条件の観察になる。一意な期待ジョブとして1反復でも成立すれば反証となる。棄却条件が観察されない`oracle-fail`は、期待観察との不一致ではあるが実行未完了ではない。timeoutや欠損は`oracle-fail`ではなく未判定なので、支持判定を止める。
- `neutral`: ハーネスや境界を確認するが、成立・不成立のどちらも仮説評価を直接動かさない。ハーネス自体の自己確認は、対象仮説を直接支持しない限りneutralにする。

性能オラクルには単発の厳密閾値を置かない。ウォームアップを分け、複数回測定し、中央値、分位点、最小・最大、外れ値の扱いを事前に決める。

## 5. 並列化する

独立条件を満たすジョブだけを同時実行する。

- 出力先がジョブ固有である。
- コンテナ名が一意である。
- 固定ポートを共有しない。
- 書き込み可能なホストディレクトリを共有しない。
- 外部APIのレート制限を超えない。
- 合計CPUとメモリがホスト容量を超えない。
- 共有API、固定ポート、書き込み状態を使うケースには同じ `exclusiveGroup` を付ける。

目安:

```text
parallelism = min(
  job_count,
  maxConcurrency,
  floor(host_logical_cpus / cpus_per_job),
  floor(usable_memory / memory_per_job),
  external_rate_limit
)
```

ランナーの `auto` はジョブ数、`maxConcurrency`、論理CPU数だけを使う。メモリと外部レート制限は自動推定しないため、マニフェスト側で `maxConcurrency` を下げる。

## 6. 段階実行する

1. **Harness smoke**: target、negative、failureを各1件。
2. **Pilot**: 全ケースを1回。
3. **Confirmation**: 不安定または重要なケースを3回以上。
4. **Scale**: 統計的な主張に必要な反復だけを追加。

Pilot失敗を見て都合よくオラクルを変更しない。変更する場合は新しいrun-idを使い、変更理由をレポートする。

## 7. 手作業で照合する

最低3件を選ぶ。

- 期待どおり合格したtarget。
- 不合格または棄却されたケース。
- 境界または負例。

各件について、入力、実行コマンド、stdout、stderr、生成物、result.jsonの判定が一致することを確認する。
