# Step 4: Refactor（コード改善）

> **目的**: テストが通る状態を維持しながら、コードの品質を向上させる

## 絶対ルール

```
【この段階でやること】
✅ テストがパスし続けることを常に確認
✅ 小さな変更 → テスト実行 → 確認 を繰り返す
✅ テストが落ちたら即座にリバート

【この段階でやらないこと】
❌ テストを変更する（仕様変更と混同しない）
❌ 新機能を追加する（それは新しいRedから始める）
```

## 改善観点

| 観点 | 確認事項 |
|---|---|
| 命名 | 変数名・関数名が意図を表現しているか |
| DRY | 重複コードがないか（ただし過剰な共通化は避ける） |
| 型安全性 | 型が適切に定義されているか |
| 可読性 | コードの流れが理解しやすいか |
| **認知負荷** | 一度に理解すべき情報量が4チャンク以内か |

## 認知負荷の最適化

> 参照: `.cursor/rules/cognitive-load-minimization.mdc`

### 判断フロー

```
リファクタ対象の複雑さは？
├─ 単純（1-2ファイル、明確な改善点）
│   → セルフチェックで対応
│
└─ 複雑（複数ファイル、設計判断が必要）
    → refactoring-specialist サブエージェントへ委譲
```

### セルフチェック項目

コードレベルで確認：

- [ ] 条件分岐は3つ以上の論理演算子を含んでいないか？
- [ ] ネストは2段階以内に収まっているか？
- [ ] 早期リターン（ガード節）で異常系を先に処理しているか？
- [ ] 各変数名は意図を明確に表現しているか？

モジュールレベルで確認：

- [ ] 一つの機能を理解するために複数モジュールを行き来する必要がないか？
- [ ] 過剰な分割で「浅いモジュール」になっていないか？

### サブエージェント委譲

複雑なリファクタリングが必要な場合は、`refactoring-specialist`を起動：

```
Task tool を使用:
- subagent_type: "refactoring-specialist"
- prompt: 対象ファイルと改善目的を指定
```

## 実行サイクル

```
1. 改善箇所を1つ特定
    ↓
2. 小さく変更
    ↓
3. テスト実行
    ↓
4. パスした → 1に戻る
   落ちた → 即リバート
```

## 完了条件

- [ ] 全テストがパスしている
- [ ] lint が通る（`pnpm <package> lint`）
- [ ] typecheck が通る（`pnpm <package> typecheck`）

## リバートの方法

```bash
# 直前の変更を取り消す
git checkout -- <file>

# または
git stash
```
