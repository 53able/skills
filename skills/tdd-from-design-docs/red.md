# Step 1: Red（失敗するテストを書く）

> **目的**: 実装すべき仕様をテストとして表現し、「正しく失敗する」状態を作る

## 絶対ルール

```
【この段階でやること】
✅ テストファイル（*.test.ts）のみを編集する
✅ Design Docsから期待動作を抽出する
✅ テストを実行して「失敗する」ことを確認する

【この段階でやらないこと】
❌ 実装コードを書く
❌ モックに「実装ロジック」を書く（スタブのみ）
```

## 実行手順

### 1. Design Docsから期待動作を抽出

- 入力と出力のペアを特定
- 正常系・異常系・境界値を洗い出す

### 2. テストケースを作成

```typescript
describe("対象機能", () => {
  it("正常系: 期待される入力に対して正しい出力を返す", () => {
    // Arrange
    const input = { /* Design Docsに基づく入力 */ };

    // Act
    const result = targetFunction(input);

    // Assert
    expect(result).toEqual({ /* 期待出力 */ });
  });
});
```

### 3. テストを実行して失敗を確認

```bash
pnpm <package> test <file>.test.ts
```

## 期待される失敗パターン

| 失敗の種類 | 意味 |
|---|---|
| `ReferenceError: xxx is not defined` | 関数が未定義（正常） |
| `TypeError: xxx is not a function` | 関数が存在しない（正常） |
| **テストがパスする** | ⚠️ テストが不十分！見直し必要 |

## 完了条件

- [ ] テストが**意図した理由で**失敗している
- [ ] 実装コードを一切書いていない
- [ ] テストケース名が日本語で意図を表現している

# Step 2: Commit（テストを固定）

> **目的**: 実装に移る前に、失敗するテストをコミットして「期待していた仕様」を記録する

## コマンド

```bash
git add <test-file>.test.ts
git commit -m "test: <機能名>の失敗テストを追加"
```

## なぜコミットするのか？

| 理由 | 説明 |
|---|---|
| テストの固定 | 実装中にテストを変えてしまう誘惑を防ぐ |
| 履歴の記録 | 「何を期待していたか」が記録される |
| ロールバック可能 | 実装がうまくいかなければテストに戻れる |
