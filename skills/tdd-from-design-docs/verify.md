# Step 5: Verify（検証）

> **目的**: 実装が仕様を正しく反映しているか最終確認し、コミットする

## オーバーフィッティング検証

> テストケースだけを通すために、本来の仕様とは異なる実装をしていないか？

### 確認観点

- [ ] テストをパスするためだけのハードコードがないか
- [ ] 仕様と異なる特殊処理がないか
- [ ] 追加すべきテストケースがないか

### 危険信号

```typescript
// ⚠️ ハードコードの例
if (input === "test-case-1") {
  return expectedOutput1;  // これはテストだけを通すための実装
}

// ✅ 正しい実装
return processInput(input);
```

## 最終コミット

```bash
git add .
git commit -m "feat: <機能名>を実装"
```

## アンチパターン集

| NG | なぜダメか | 対策 |
|---|---|---|
| 実装しながらテストを書く | テストが実装に引きずられる | Red を徹底 |
| モックに実装を書く | テストが仕様を反映しない | スタブのみ |
| Green で完璧を目指す | 目的がブレる | 「動く」だけ |
| Refactor でテストを変える | 仕様変更と混同 | テストは固定 |
| テストをパスするためのハードコード | 仕様を満たしていない | Verify で検出 |

## TDD成功の指標

| 指標 | 良い状態 |
|---|---|
| Red → Green の時間 | 短い（5-15分） |
| Refactor の頻度 | 高い（小さく何度も） |
| テストの失敗理由 | 常に意図通り |
| コミット粒度 | 小さい（フェーズごと） |
