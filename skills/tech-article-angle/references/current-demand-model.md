# 現在の技術記事需要モデル

このモデルは、記事テーマを、現在の技術記事として読まれやすい論点へ運ぶために使う。

## 需要レーン

### 1. AI導入後の実務摩擦

AI coding、コーディングエージェント、自動生成が日々の開発を変えるテーマで使う。

読者の問い:
- AIで実装が速くなった後、何が壊れるか。
- レビュー、テスト、CI/CD、セキュリティ、ドキュメントはどう変えるべきか。
- どの作業は人間の判断として残すべきか。

記事を強くする証拠:
- レビューチェックリスト
- CI設定
- セキュリティスキャン結果
- Before/After のワークフロー
- 失敗した自動化の例
- 後から見つかった保守上の問題

### 2. 検証と責任

正しさ、リスク、意思決定、責任が主題になる場合に使う。

読者の問い:
- 出力をどう検証するか。
- 何をAIに委ねないか。
- 受け入れ基準は何か。
- 誰がデプロイ判断をするか。

記事を強くする証拠:
- テストケース
- ログ
- Mutation testing の結果
- 手動レビューの基準
- インシデントまたはヒヤリハット
- 意思決定記録

### 3. 実測改善

性能、コスト、信頼性、トークン、ビルド、作業時間などを改善できるテーマで使う。

読者の問い:
- 何が遅い、高い、不安定、面倒だったか。
- 何を変えたか。
- 結果をどう測ったか。
- どんなトレードオフが出たか。

記事を強くする証拠:
- Before/After の数値
- 実行コマンド
- 環境情報
- 設定差分
- 失敗した試行
- 再現性メモ

### 4. ワークフロー再設計

ツールによって、仕様、コード、レビュー、ドキュメント、リリースの作り方が変わる場合に使う。

読者の問い:
- 古いワークフローのどこが合わなくなったか。
- 新しい受け渡しや成果物は何か。
- チームはどう混乱を避けるか。
- 何が楽になり、何が難しくなったか。

記事を強くする証拠:
- プロセス図
- テンプレート
- Pull request 例
- 会議またはレビューの流れ
- チームルール
- 導入失敗例

### 5. データと業務アクションの設計

AIがデータシステム、オントロジー、セマンティックレイヤー、ナレッジグラフ、業務アクションに接続する場合に使う。

読者の問い:
- システムは質問に答えるだけか、業務アクションを支えられるか。
- どんな意味、権限、監査ログが必要か。
- human-in-the-loop は何を承認するか。
- 業務の現実をどうモデル化するか。

記事を強くする証拠:
- ドメインモデル
- オントロジー例
- Action type の定義
- 承認フロー
- 監査証跡
- データ品質の失敗例

### 6. キャリアと組織の地図

エンジニアの役割、チーム構造、学習戦略がテーマの場合に使う。

読者の問い:
- どの仕事が安くなるか。
- どの仕事の価値が上がるか。
- 若手は何を学び続けるべきか。
- チームは何を設計し直すべきか。

記事を強くする証拠:
- 具体的な役割変化
- チームワークフロー例
- 採用基準またはレビュー基準
- スキルマトリクス
- Before/After の責任分担

## 採点基準

各候補を0〜3点で採点する。

- 読者の痛み: 読者が問題をすぐ認識できるか。
- 時事性: AI時代の実務圧力に接続しているか。
- 証拠の道筋: 数字、設定、ログ、例、判断を示せるか。
- 転用性: 別の開発者やチームが学びを再利用できるか。
- 具体性: 一般的なトレンド論に留まっていないか。

推奨しきい値: 11/15点以上。

## 避ける型

ユーザーが明示的に求めない限り、次の型は避ける。

- ツール名 + 「使ってみた」だけで、ワークフロー上の帰結がない記事
- 検証、失敗、運用詳細のないAI礼賛
- 判断カテゴリのないキャリア不安
- 文脈やトレードオフのないベストプラクティス集
- 具体的な読者メリットが見えない汎用タイトル
