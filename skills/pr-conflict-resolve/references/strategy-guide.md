# Merge vs Rebase 戦略ガイド

## 判断マトリクス

| 判断基準 | Merge | Rebase |
|---|---|---|
| 他の開発者と共有しているブランチ | 安全 | **危険** — 履歴を書き換える |
| 履歴のスタイル | 実際のマージグラフが残る | 一直線でクリーン |
| コンフリクト解消の追跡容易性 | マージコミットが解消時点を記録 | マージコミットなし、追跡が難しい |
| force push の要否 | 不要 | 必要（`--force-with-lease`） |
| 操作の中断コマンド | `git merge --abort` | `git rebase --abort` |

## Merge を使うべきケース
- featureブランチをすでにプッシュ済みで、他の開発者がチェックアウトしている可能性がある。
- チームが実際の開発経緯を忠実に残す、改変しない履歴を好む。
- CIがブランチを監視しており、force push が意図しないパイプライン再トリガーを引き起こす。

## Rebase を使うべきケース
- ブランチが**ローカルのみ**か、単独開発者が使用することが明確にわかっている。
- チームがマージ前に一直線のコミットグラフを要求する運用ルールを持っている。
- PR の最終マージが squash-and-merge のため、中間履歴は捨てられる。

## `--force-with-lease` vs `--force`

| オプション | 挙動 |
|---|---|
| `--force` | リモートを無条件に上書き。チームメンバーの作業を無言で破壊する。 |
| `--force-with-lease` | リモートの先端が最後に把握した ref と一致するかチェックし、他者がプッシュしていた場合は中断する。常にこちらを使う。 |

## チーム方針確認チェックリスト
コンフリクト解消を開始する前に確認する:
- [ ] このブランチで rebase が許可されているか？
- [ ] 一直線履歴を要求するブランチ保護ルールが設定されているか？
- [ ] CIパイプラインが force push に対してすべてのチェックを再トリガーせずに対応できるか？
