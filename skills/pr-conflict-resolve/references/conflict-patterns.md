# コンフリクトパターン詳細と復旧リファレンス

## コンフリクトパターン一覧

### 同一行の競合
2人の開発者が同じファイルの全く同じ行（設定値や `README.md` など）を同時に変更した場合に発生する。

**症状:** 単一の論理行にコンフリクトマーカーが挿入される。  
**解消方針:** どちらか一方を採用するか、双方の意図を1行に統合する。

### 変更と削除の衝突
一方の開発者がファイルを変更し、もう一方がそのファイルを削除した場合に発生する。

**症状:** `git status` に "deleted by us" または "deleted by them" が表示される。  
**解消手順:**
- ファイルを残す場合 → `git add <ファイル名>`
- 削除を受け入れる場合 → `git rm <ファイル名>`

### 長寿ブランチの乖離
featureブランチが数週間にわたって開かれた間に、`main` に大規模な構造リファクタが蓄積された場合に発生する。

**症状:** 多数のファイルにわたって大量のコンフリクトハンクが発生する。  
**解消戦略:**
1. `git log --oneline origin/main` でリファクタのコミットを特定する。
2. リファクタ直前のコミットまで段階的に同期→解消→繰り返すインクリメンタルマージを行う。
3. 乖離が極端に大きい場合はfeatureブランチをより小さいPRに分割することを検討する。

### フォーマッタ適用による差分
一方のブランチでコードフォーマッタ（Prettier・gofmt など）を一斉適用し、もう一方が手動でロジックを追加した場合に発生する。

**症状:** 意味上の差異がない空白・インデントのコンフリクトが大量に発生する。  
**解消戦略:**
1. 空白のみの変更ハンクはフォーマッタ適用側を採用する。
2. 手動で追加したロジック変更をフォーマット済みコードに改めて適用する。
3. 再発防止のためフォーマッタ実行をCIに強制する。

## やりがちなミスと防止策

| ミス | 影響 | 防止策 |
|---|---|---|
| `<<<<<<<` マーカーをファイルに残したままコミット | ビルド・テスト失敗、壊れたコードのリリース | コミット前に `rg` またはスキル同梱の `./scripts/check-markers.sh` でスキャン |
| 相手側の変更を握りつぶす | 機能喪失またはバグの混入 | 双方の変更を読んでから最終形を決める |
| dirty な状態でマージを開始する | マージ中断または状態の破損 | 必ず `git status` で確認してから開始 |
| 共有ブランチで rebase + force push | チームメンバーのローカル履歴が破壊される | 他の人が使用中のブランチは絶対に rebase しない |
| `.orig` 一時ファイルを誤ってステージ | リポジトリにゴミファイルがコミットされる | `*.orig` を `.gitignore` に追加する |

## 復旧コマンドリファレンス

| 状況 | コマンド |
|---|---|
| マージを途中で中断 | `git merge --abort` |
| リベースを途中で中断 | `git rebase --abort` |
| バックアップブランチに完全リセット | `git reset --hard backup-feature-branch` |
| コミット済みのミスを取り消す | `git reflog` → `git reset --hard HEAD@{n}` |
| 特定ファイルをHEADの状態に復元 | `git restore <ファイル名>` |
| 誤ってステージしたファイルを取り消す | `git restore --staged <ファイル名>` |
