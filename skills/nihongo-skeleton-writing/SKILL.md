# 日本語骨格ライティング

## 手順

**ステップ1: 文章の仕事を固定する**
1. ジャンルを特定する。Web記事、エッセイ、レポート、解説文、ビジネス文書、その他の日本語文章のどれかを判断する。
2. 想定読者、読者が抱えていそうな疑問、読後に起こしたい変化を特定する。
3. 長文Web記事の場合は、文の磨き込みより先に、読者メリットとタイトルの強さを優先する。
4. 原文の語順や文を厳密に保持する必要がある場合は、構造リライトではなく軽い校正でよいか確認する。

**ステップ2: 根拠と制約を守る**
1. 出典リンクは、支えている主張の近くに置く。
2. 引用、書籍内容、数値、例、出典を作らない。
3. 不確かな主張は、不確かであること、または解釈であることを明示する。
4. 必須の引用、免責、法的表現、事実上の caveat は、ユーザーが明示的に削除を求めない限り保持する。

**ステップ3: 縮約マップを作る**
1. 別ファイルで改稿メモや監査記録を残す必要がある場合は、`assets/revision-template.md` を読む。
2. 文章全体を一文に縮約する。
3. 導入部を三文に縮約する。
4. 各セクションを一文に縮約する。
5. 各段落を一文に縮約する。
6. 縮約したときに主筋が消える場合は、言葉を磨く前に順序と構成を組み直す。

**ステップ4: 単語への感度を点検する**
1. 意味ではなくリズムのために置き換えられた類義語を見つける。
2. 読者が指示対象を推測できない抽象語は、具体例、場面、用例に戻す。
3. 名詞と動詞、形容詞と名詞の結びつきが自然か確認する。
4. 装飾的な難語より、なじみがあり精度の高い語を優先する。
5. 本格的な改稿では、`references/checklist.md` を読み、単語、文、段落、縮約のチェックリストを使う。

**ステップ5: 文の向きを点検する**
1. 分かりにくい文の主題を特定する。
2. 分かりにくい文の焦点を特定する。
3. 修飾語を、修飾先の近くへ移す。
4. 文頭が作った期待を、文末が回収するように書き直す。
5. 複数の役割を抱えた文は、長さに明確な意図があり読みやすい場合を除いて分ける。

**ステップ6: 段落の役割をラベル付けする**
1. 下書きがファイルとして存在し、段落の役割を体系的に確認する必要がある場合は、`python3 scripts/paragraph-labels.py [path]` を実行する。
2. 各段落に、問題、背景、定義、例、原因、反論、手順、注意、限界、結論など、一つの役割を付ける。
3. 役割が重複する段落は、反復に意図がある場合を除いて統合する。
4. 複数の役割を持つ段落は、融合によってリズムや強調がよくなる場合を除いて分割する。
5. 読者の疑問に奉仕していない段落は削る。

**ステップ7: 敬語を関係性の設計として見直す**
1. 各文で、誰が動作するのかを特定する。
2. 誰に向けた文で、誰に敬意を示しているのかを特定する。
3. 責任、依頼、行動を隠すだけの装飾的な敬語を削る。
4. 依頼文は、相手が行動できる程度に直接的にする。
5. ユーザーが丁寧語を好む場合は丁寧な文体を保つ。ただし、丁寧さで意味をぼかさない。

**ステップ8: 改稿版を出す**
1. タイトルは、読者メリットまたは読むべき緊張を示す形に強める。
2. ジャンル上必要な場合を除き、レポート調の導入を、読み続ける理由が分かる導入に置き換える。
3. 出典は、支えている主張の近くに残す。
4. 余分な前置き、定型的な対比、曖昧な称賛、AIらしい cadence を削る。
5. ユーザー意図とファイルサイズに応じて、全文改稿または部分差分を出す。
6. ファイルを編集した場合は、完了報告の前に改稿ファイルの存在と変更箇所を確認する。

## エラー処理

* 根拠付きの主張を確認できない場合は、caveat として残すか削除する。
* 読者像がまったく定まらない場合は、深い改稿の前に想定読者を確認する。
* 段落ラベル用スクリプトがファイル未発見で失敗した場合は、下書きの場所を探すか、正しいパスを確認する。
* 縮約によって論旨の骨格が回収できない場合は、行単位の校正より先に構成変更を提案する。
* 求められた改稿が必須の引用や免責を消す場合は、それらを保持し、制約を説明する。
