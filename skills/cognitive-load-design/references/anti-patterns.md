# 認知負荷アンチパターン 診断チェックリスト

レビュー対象のコード・設計に対して以下の問いを投げかける。
該当するほど外来的認知負荷（Extraneous Cognitive Load）が高い。

---

## A. コードレベル

### A1. 複雑な条件式
- [ ] `&&` / `||` が3つ以上連続している
- [ ] 条件に否定（`!`）が2つ以上混在している
- [ ] 条件の意味をコメントなしに即座に説明できない

→ **対処:** スキル同梱の `references/cognitive-load-patterns.md` の Pattern 1 を参照

### A2. 深いネスト
- [ ] if ネストが3段以上ある
- [ ] ハッピーパスが最も深い位置にある
- [ ] エラー処理のために最後まで読まないと全体が把握できない

→ **対処:** スキル同梱の `references/cognitive-load-patterns.md` の Pattern 2 を参照

### A3. 意味不明な数値・コード
- [ ] HTTP ステータスコードでビジネスロジックを表現している
- [ ] DB に数値ステータス（0=active, 1=inactive, 2=deleted）が直接格納されている
- [ ] エラーコードが整数で、ドキュメントなしに意味が分からない

→ **対処:** スキル同梱の `references/cognitive-load-patterns.md` の Pattern 5 を参照

---

## B. モジュール・クラスレベル

### B1. 継承の深さ
- [ ] 継承ツリーが3段以上ある
- [ ] あるクラスを理解するために複数の祖先クラスを読む必要がある
- [ ] 子クラスを変更すると孫クラスへの影響を確認しなければならない

→ **対処:** スキル同梱の `references/cognitive-load-patterns.md` の Pattern 4 を参照

### B2. 浅いモジュールの乱立
- [ ] クラス/モジュール数がコード行数に対して異常に多い（例: 5000行で80クラス）
- [ ] クラス名が3語以上の連結でインタフェースより長い
- [ ] 一つの機能を実現するために5ファイル以上を横断している

→ **対処:** スキル同梱の `references/cognitive-load-patterns.md` の Pattern 3 を参照

### B3. DRY 過剰適用
- [ ] 関係のないビジネスドメイン間で共通クラス/関数を共有している
- [ ] 「似ているから」という理由だけで統合された処理がある
- [ ] ライブラリを使うために10段以上のスタックトレースを追う必要がある

→ **対処:** スキル同梱の `references/cognitive-load-patterns.md` の Pattern 6 を参照

---

## C. アーキテクチャレベル

### C1. フレームワーク密結合
- [ ] ビジネスロジックがフレームワーク固有のクラスを直接継承している
- [ ] フレームワークを知らないと単体テストが書けない
- [ ] フレームワーク固有の「マジック」なしにコアロジックが動かない

→ **対処:** スキル同梱の `references/cognitive-load-patterns.md` の Pattern 7 を参照

### C2. レイヤードアーキテクチャの過剰適用
- [ ] 1つの機能追加で4ファイル以上を同時に変更しなければならない
- [ ] Port/Adapter の用語を学ばないとコードを理解できない
- [ ] 抽象化が複雑さを隠しているのではなく、間接参照を増やしているだけ

→ **対処:** スキル同梱の `references/cognitive-load-patterns.md` の Pattern 8 を参照

### C3. マイクロサービスの過細分化
- [ ] 1つの要件変更で4サービス以上を変更する必要がある
- [ ] ローカル環境でシステム全体を再現するのに30分以上かかる
- [ ] サービス数がチームのエンジニア数を大きく超えている

→ **対処:** まず well-crafted monolith を検討する。分離の必要性（スケール、デプロイ頻度、チーム境界）を明示的に評価する。

---

## D. 設計意思決定レベル

### D1. ユニークなメンタルモデルの数
- [ ] 新しいメンバーが迷子になる時間が40分以上連続する
- [ ] プロジェクト固有の独自解釈のアーキテクチャが存在する
- [ ] ドキュメントを読まないと基本的な変更の場所が分からない

**判定基準:** 新メンバーが数時間以内に最初のコントリビューションを出せるか？

### D2. 熟知バイアスの確認
- 「これは分かりやすい」は自分が慣れているだけかもしれない
- 新しいメンバーにペアプロを依頼して混乱した箇所を計測する
- 1.5年後に自分がそのコードを読んだとき把握できるか想像する
