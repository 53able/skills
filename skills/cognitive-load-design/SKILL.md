# 認知負荷を制するコード設計ガイド

> ヒューマンの作業記憶は約4チャンク。それを超えると 🤯 になる。
> 削減できるのは **外来的負荷 (Extraneous)** だけ。設計の癖や情報の提示方法が原因のもの。

---

## 手順

### Step 1: スコープを確定する

1. 対象（ファイル・モジュール・サービス・アーキテクチャ全体）を特定する。
2. 作業の目的を以下のいずれかに分類する:
   - **A. コードレビュー** — PR 差分を対象に認知負荷シグナルを検出する
   - **B. 設計レビュー** — 新規設計案を対象にアンチパターンを事前評価する
   - **C. リファクタリング** — 既存コードの認知負荷を削減する
3. 目的が A または C であれば **Step 2 へ**。目的が B であれば **Step 3 へ**スキップする。

---

### Step 2: 定量シグナルを収集する（A・C の場合）

スクリプトを実行して認知負荷の高いコード箇所を洗い出す:

```bash
python3 scripts/check_load.py [対象ディレクトリ]
```

出力された各カテゴリの検出結果を記録する。次のステップで優先順位をつける。

---

### Step 3: アンチパターンを診断する

スキル同梱の `references/anti-patterns.md` を読み、以下のカテゴリでチェックを行う:

| カテゴリ | 対象 |
|----------|------|
| **A. コードレベル** | 複雑な条件式・深いネスト・数値ステータス |
| **B. モジュールレベル** | 継承の深さ・浅いモジュールの乱立・DRY 過剰 |
| **C. アーキテクチャ** | フレームワーク密結合・レイヤー過剰・マイクロサービス過細分化 |
| **D. 設計意思決定** | ユニークなメンタルモデルの数・熟知バイアス |

各チェック項目に該当する箇所を列挙し、重篤度（🧠+〜🤯）を付与する。

---

### Step 4: リファクタリング方針を決定する

検出した問題ごとにスキル同梱の `references/cognitive-load-patterns.md` の対応パターンを参照する:

| 問題 | 参照パターン |
|------|-------------|
| 複雑な条件式 | Pattern 1: 中間変数による条件式の分解 |
| 深いネスト | Pattern 2: アーリーリターンによるネスト解消 |
| 浅いモジュール乱立 | Pattern 3: 深いモジュール vs 浅いモジュール |
| 継承地獄 | Pattern 4: 継承よりコンポジション |
| 数値ステータスコード | Pattern 5: 自己記述的なステータスコード |
| DRY 過剰適用 | Pattern 6: DRY の過剰適用を避ける |
| フレームワーク密結合 | Pattern 7: フレームワークを外側に置く |
| レイヤードアーキテクチャ濫用 | Pattern 8: レイヤードアーキテクチャの費用対効果 |

---

### Step 5: リファクタリングを実施する（C の場合）

優先度の高い箇所から着手する。判断基準:

1. **影響範囲が広い（多くの開発者が読む箇所）** → 最優先
2. **新メンバーが混乱する箇所** → 次点
3. **変更頻度が高いホットスポット** → 高頻度で読まれる

各パターンの適用前・適用後でコードを示し、認知負荷の変化（🧠 の数）を明示する。

---

### Step 6: 設計原則の評価（B・アーキテクチャ見直しの場合）

以下の問いで設計の認知負荷を評価する:

```
1. 新メンバーは数時間以内に最初のコントリビューションを出せるか？
2. バグの再現・デバッグ時にコールスタックを何段追う必要があるか？
3. 要件変更時に変更が必要なファイル数はいくつか？
4. このアーキテクチャを理解するために学ぶユニークなメンタルモデルは何個か？
```

**望ましい設計の特徴:**
- 深いモジュール（シンプルなインタフェース、複雑な実装を隠蔽）
- 単方向の依存関係
- ビジネスロジックがインフラ（DB・フレームワーク・UI）に依存しない
- 退屈なほど予測可能なコード（Unix・Linux・Redis の設計を参考にする）

---

### Step 7: レビューコメントを作成する（A の場合）

各指摘は以下の形式で記述する:

```
[認知負荷シグナル] <ファイル名:行番号>
- 現状: <何が問題か> (🧠+++ or 🤯)
- 原因: <なぜ認知負荷が高いか>
- 提案: <具体的なリファクタリング案> (🧠 or 🧠+)
- 参照: スキル同梱の references/cognitive-load-patterns.md Pattern N
```

---

## 重要な原則（常に念頭に置く）

- **固有的負荷は削減できない** — ドメインの本質的な複雑さを単純化しようとしない
- **外来的負荷だけを狙い撃ちにする** — 著者の癖・不必要な抽象化・トレンドの乱用
- **熟知バイアスに注意する** — 自分が慣れているコードは「簡単」に感じるが、新メンバーには 🤯 かもしれない
- **退屈さは美徳** — 一番良いコードは読んで即座に把握できるコード
- **レイヤーはタダではない** — 抽象化を加えるたびに作業記憶のコストが上がる

---

## エラーハンドリング

- **スクリプトが動かない場合:** `rg` (ripgrep) がインストールされているか確認する。`brew install ripgrep`
- **検出結果が多すぎる場合:** まず D1（ユニークなメンタルモデルの数）から評価し、アーキテクチャレベルの問題を優先して解消する
- **パターンの適用が難しい場合:** 「このコードを初見の開発者が5分で理解できるか？」を問い直し、できないなら認知負荷が高い
- **「これは仕様だから仕方ない」と言いたくなる場合:** 固有的負荷か外来的負荷かを区別する。仕様の複雑さ（固有的）は変えられないが、その表現方法（外来的）は変えられる
