900x460 の白背景に日本語ゴシック 28px で以下9行を描画したもの。

`detection_count: 19`（重複bbox含む）、終了コード 0、再OCR検証で残存なし。

## 観測された問題と対処

### OCR 誤読による検出漏れ

`example.co.jp` が `example.coJjp` と読まれ、Presidio 標準の `EMAIL_ADDRESS`
（TLD を検証する）が不発だった。TLD を検証しない `EMAIL_LOOSE` パターンを追加して救済した。
同種の漏れは他の厳密パターンでも起こりうる。**OCR 誤読は原理的に残るリスク**。

`sk-abcdefghijklmnopqrstuvwxyz012345` は `...ijkImnop...`（l→I）と誤読されたが、
`sk-[A-Za-z0-9_-]{20,}` は文字種を限定しないため検出できた。文字種を厳しくすると壊れる。

### OCR の単語分割

Tesseract は日本語をスペース区切りの単語列として返すため、`東京都渋谷区` は
`東京 都 渋谷 区` になる。当初の住所パターンはスペースを許可しておらず不発だった。
現行パターンは `\s?` を挟んでいる。**日本語向け正規表現を追加する際は必ずスペース混入を想定する。**

### 住所パターンの貪欲マッチ

初期版は `東京 都 渋谷 区 神南 1-2-3 電話 : 090-1234-5` まで巻き込んで次の行に侵入した。
文字クラスから `:` `：` を除外して抑制した。それでも末尾のラベル語（`電話`）は巻き込む。
安全側の誤りだが、必要な情報も消える点は運用で許容するか要判断。

### 検証機構の妥当性確認

`verify()` を直接呼び、同一の検出結果に対して

- 未マスク画像 → `[{'entity_type': 'JP_PHONE', 'text': '090-1234-5678'}]`（漏れを検出）
- マスク済み画像 → `[]`

を確認した。検証は再OCR文字列の部分一致で、4文字未満の検出は判定対象外。

### 検証の穴

`--fill 255,255,255` を白背景画像に適用すると、文字は消えるが視覚的な塗りつぶし跡が
残らない。この場合も検証は通過する。**検証通過は「文字が読めない」ことの確認であり、
「意図した領域が視認できる形で隠されている」ことの確認ではない。**

### EXIF

`Make` と `GPSLatitudeRef` を含む JPEG を入力した場合、出力 PNG の EXIF エントリ数は 0 だった。
出力を PNG に固定しているため、入力側のメタデータは伝播しない。
元画像そのものを共有する運用では別途 `exiftool` 等で除去が必要。

### 検出0件の扱い

PII を含まない画像（`Build succeeded in 12s`）では検出0件・終了コード3を返した。
終了コード3は「安全」ではなく「未検証」を意味する設計にしている。

# 実測デモ2: CRM画面風スクリーンショット（1000x620）

成果物: `~/outputs/image-pii-masking-demo/`（`before.png` / `dryrun.png` / `after.png` / `compare.png`）

`sk-` APIキー、AWSアクセスキー、内部IP、DBユーザー名、Slackトークン入りWebhook URL。

## 1周目（単一パス `--psm 6`、修正前の既定）

検出24件。**WEBHOOK行が丸ごと未検出**だった。OCRテキストに `WEBHOOK` も `xoxb`
も現れず、行末は `に` と誤読されていた。同じ行を切り出して単独OCRすると
`WEBHOOK=https://...xoxb-9876543210-abcdefghij` と正しく読める。
つまり**画像全体のレイアウト解析が特定行を捨てていた**。

`--psm 3/4/6/11/12`、`-l eng` 単独、`-l eng+jpn` をすべて試しても全画面では復旧せず。
`2倍拡大 + --psm 3` で初めて復旧した。

## 2周目（`psm 3` 単独に変更）

`xoxb-9876543210-abcdefghij` と `鈴木 花子` を新たに検出。
一方で `sk-abcdefgh1jkLmnopqrstuvwxyz912345` と `AKIATOSFODNN7EXAMPLE` の検出が消えた。
読み取り順が変わり、`CRM_API_KEY=sk-...` が別トークンに分断されたため。

**結論: PSM の選択は取捨選択になり、単一パスでは安全側に振れない。**
既定を `--ocr-pass 3:2` と `--ocr-pass 6:1` の union に変更した。

## 3周目（複数パス union、現行既定）

| パス | ocr_text_length | boxes | 新規boxes |
|---|---|---|---|
| psm 3 / 2x | 488 | 28 | 28 |
| psm 6 / 1x | 465 | 24 | 18 |

union で 46件。`sk-` `AKIA` `xoxb` `鈴木 花子` `田中 太郎` 住所 電話 メール
IP 〒 をすべて捕捉した。

## 残った取りこぼしと最終対処

| 取りこぼし | 原因 | 対処 |
|---|---|---|
| `タナカ タロウ`（フリガナ） | OCRが `タナ カ タロ ウ` に分割。deny-listの文字列一致が効かない | `--mask-box 176,166,230,30` |
| `1985年4月12日`（生年月日） | `DATE_TIME` が既定エンティティに無い | `--entities` に `DATE_TIME` 追加 |
| `crm_admin`（DB_USER） | パターン未定義 | `--deny-list-file` + `--extra-pattern 'DB_CRED=DB_USER=\S+'` |

最終実行は検出75件・手動box 1件・終了コード0・再OCR検証で残存なし。

## 副作用（塗り過ぎ）

`DATE_TIME` を有効にすると `開始日: 2024年10月1日`（非PII）も消える。
`LOCATION` の誤検出で `契約ID: CT-2024-000871` と `更新区分` の一部も塗られた。
`プラン` `月額` `累計売上` は保持された。
**塗り過ぎは受容し、塗り漏れは受容しない**という方針の直接の帰結。
資料としての可読性が要る場合は `--allow-list` で個別に戻す。

## 4周目: `DATE_TIME` の撤回とラベル基準マスク（レビュー指摘による修正）

3周目の出力をレビューして「生年月日がマスクされているのは要らない」という指摘を受け、
`after.json` の座標を確認したところ、`DATE_TIME` が**ラベル文字そのもの**を塗っていた。

| 検出テキスト | 座標 | 実体 |
|---|---|---|
| `年 月 日` | x=84,y=205 / x=103,y=206 | **ラベル「生年月日」の「年」「月」** |
| `状態 年 月 1985 年 4 月 12 日` | x=646,y=173 | **「契約状態」の「状態」** |
| `2024 年 10 月 1 日` | x=739..890,y=198 | **非PIIの「開始日」** |

つまり `DATE_TIME` は1つのエンティティ指定で3種類の巻き込みを起こしていた。
ラベルが塗られると「何を伏せたのか」が読み手に伝わらず、資料としての価値も落ちる。

### 対処

1. `DEFAULT_ENTITIES` から `DATE_TIME` を除外（コメントで理由を明記）
2. `--mask-right-of 'LABEL[:WIDTH]'` を実装。OCR語を視覚的な行にグルーピングし、
   連結文字列からラベルを検索、ラベル最右端の右側から指定幅を塗る。
   ラベル自体は無傷で残る
3. `LOCATION` の誤検出（契約ID `CT-2024-000871` の `000871` を地名と判定）は
   `--allow-list` で個別に解除

### 結果比較

| 版 | 設定 | 検出数 | 生年月日ラベル | 開始日(非PII) | 契約ID(非PII) |
|---|---|---|---|---|---|
| 3周目 | `DATE_TIME` 有効 | 75 | 塗られる | 塗られる | 塗られる |
| A | `DATE_TIME` 除外 | 48 | 無傷 | 無傷 | 塗られる |
| B | A + `--mask-right-of 生年月日:220` | 48(+manual 2) | 無傷・値のみ塗り | 無傷 | 塗られる |
| C | B + `--allow-list 更新 000871 CT-2024-000871` | 45 | 無傷・値のみ塗り | 無傷 | 無傷 |

C は左カード内のPIIをすべてマスクしつつ、全ラベルと右カード（契約サマリ）を完全保持。
検証は全版で残存なし・終了コード0。成果物は `after_A.png` / `after_B.png` / `after_C.png`。

**教訓: エンティティ種別を足して再現率を上げる発想は、ラベル/値レイアウトでは逆効果になる。
位置構造を使えるなら、位置構造で解く。**

## この検証で見つけた不具合2件

### 1. 負値 `--pad` で未処理例外（修正済み）

`--pad -9` で `ValueError: y1 must be greater than or equal to y0` が発生し、
**レポートJSONも書かれずに終了コード1で異常終了**した。
マスク処理の失敗時にレポートが残らないのは監査上まずい。
`render()` で矩形を `x1 > x0`, `y1 > y0` にクランプするよう修正。
修正後は `--pad -9` → 終了コード2＋残存10件を正しく報告する。

### 2. `--pad` が明示指定ボックスまで膨張させていた（修正済み）

`--mask-right-of` で作った LABEL_VALUE ボックスにも `--pad 4` が適用され、
マスク開始位置がラベル側へ4px侵入していた（x=117 → x=113）。
`MANUAL` と `LABEL_VALUE` は明示指定なので pad を適用しないよう修正。

**ただし影響は装飾的だった。** 侵入した領域のインク破壊画素は修正前も **0** で、
4pxはラベルと値の間の余白に収まっていた。ラベル文字が実際に欠けていたわけではない。

## セルフテストの導入

上記の一連の検査を `scripts/selftest.py` に固定した（34項目、約13秒）。

- MASK 12領域: 元画像のインク画素が全て変化したか（残存0を要求）
- KEEP 11領域: ラベル・非PIIのインク画素が1つも改変されていないか（改変0を要求）
- 終了コード契約: 正常0 / 塗り不足2 / 検出0件3
- 検証器の健全性: 未マスク画像では残存を検知し、マスク済みでは検知しない
- 既定エンティティに `DATE_TIME` が入っていないこと
- 出力PNGにEXIFが残らないこと

最終結果: **34項目中34合格（終了コード0）**。

## 検証中に見つけたテスト側の誤り2件（製品側の問題ではない）

1. 当初のピクセル検査は「領域の平均輝度 < 12」を条件にしており、住所・電話番号・
   担当営業の3領域が不合格になった。3倍拡大して目視したところ残っていたのは**白背景**で、
   文字インクの残存ではなかった。手で推定した領域が実際の文字範囲より広すぎたため。
   判定基準を「元画像のインク画素が変化したか」に変更して解消した。
2. `DEFAULT_ENTITIES` の検査をソース文字列の切り出しで行ったため、リスト内の
   コメント文中の `DATE_TIME` を誤検出した。モジュールを import して実体のリストを
   参照する方式に変更した。

**教訓: マスキングの検証で「平均輝度」のような間接指標を使うと、
背景の白さで合否が動く。元画像のインク画素を追跡する直接指標を使う。**

# 追加検証: PII以外の機密値（金額）のマスク

「契約サマリの金額を消したい」という要望に対し、コード変更なしで対応できるか3経路を実測した。

| 経路 | 指定 | 結果 |
|---|---|---|
| 正規表現 | `--extra-pattern 'JP_MONEY=[0-9][0-9,\. ]{2,}\s?円'` | **成功**。`480,000 円` `5,760,000 円` を捕捉 |
| ラベル基準 | `--mask-right-of '月額:240' --mask-right-of '売上:230'` | **成功**（ただし下記の注意あり） |
| NER | `--entities ... MONEY` | **不発**。`ja_core_news_sm` は金額を MONEY とタグ付けしない |

最終コマンド（通常のPIIマスク + 金額）は検出52件・終了コード0・残存なし。

## ピクセル検証（`after_with_money.png`）

| 領域 | 期待 | 結果 |
|---|---|---|
| 月額の値 | マスク | インク739px 残存0 |
| 累計売上の値 | マスク | インク811px 残存0 |
| ラベル『月額』 | 保持 | インク286px 改変0 |
| ラベル『累計売上』 | 保持 | インク430px 改変0 |
| プラン / 契約状態 / 開始日 / 契約ID / 更新区分 | 保持 | すべて改変0 |

## この検証で判明した `--mask-right-of` の2つの注意点

### 1. ラベルのOCR誤読で不発になる

`累計売上` が **`索計売上`**（累→索）と読まれており、`--mask-right-of '累計売上'` は一致しなかった。
`--mask-right-of '売上'` のように**短い部分文字列**を使うと通る。
ラベル指定は長く正確に書くほど脆い。

### 2. 行グルーピングは左右のカードを連結する

OCR行の連結結果は以下のように**左カードと右カードが同一行**になる。

```
'生年月日1985年4月12日開始日2024年10月1日'
'郵便番号〒150-0041月額480,000円'
'住所東京都渋谷区神南1-2-3ハイツ渋谷402索計売上5,760,000円'
'メールtaro.tanaka@example.co.jp契約IDCT-2024-000871'
```

このため `--mask-right-of` の WIDTH を大きくとりすぎると隣のカラムまで塗る。
必ず dry-run で幅を確認する。実測での適正値は `月額:240` `売上:230`（アンカー右端からの距離）。

# 依存の隔離（uv）

## 当初の状態: 隔離できていなかった

指摘を受けて確認したところ、スクリプトに依存宣言が無く、**外部で有効化した venv に
暗黙依存**していた。素の環境での実測:

```
$ python3 scripts/mask_image.py --help
ModuleNotFoundError: No module named 'PIL'
$ uv run scripts/mask_image.py --help
ModuleNotFoundError: No module named 'PIL'
```

それまでの検証はすべて手動で `. .venv/bin/activate` した状態に依存していた。
スキルとして配布する上での欠陥。

## 対処: PEP 723 インラインメタデータ

`mask_image.py` と `selftest.py` の両方に依存宣言とバージョン固定を埋め込み、
shebang を `#!/usr/bin/env -S uv run --script` に変更した。

```
requires-python = ">=3.10,<3.13"
presidio-image-redactor==0.0.60
presidio-analyzer==2.2.364
pillow>=10.0,<14
spacy>=3.8,<3.9
ja_core_news_sm @ https://.../ja_core_news_sm-3.8.0-py3-none-any.whl
```

## 隔離後の実測

| 検証 | 結果 |
|---|---|
| `VIRTUAL_ENV` 未設定の素の環境で `uv run --script mask_image.py --help` | 成功（76パッケージを226msで解決） |
| shebang 直接実行 `./mask_image.py --help` | 成功 |
| 同環境でセルフテスト全体 | **34項目中34合格**（初回58秒、依存解決込み） |
| 解決された環境 | Python 3.12.12 / `~/.cache/uv/environments-v2/...` に隔離 |
| 実際の版 | presidio-analyzer 2.2.364, presidio-image-redactor 0.0.60, pillow 12.3.0, spacy 3.8.14, ja-core-news-sm 3.8.0, pytesseract 0.3.13 |
| 隔離実行の出力 | ハッシュ `fdd14d4e7880609e` — venv 手動有効化時の成果物とバイト一致 |

## 隔離されないもの

**Tesseract 本体はシステムバイナリなので uv の管理外。** `/opt/homebrew/bin/tesseract`
が使われる。OCR結果はTesseractの版とtraineddataで変わるため、
Tesseractを更新したらセルフテストを再実行する必要がある。
pytesseract（Pythonラッパ）は隔離されるが、呼び出す先のバイナリは隔離されない。

## 副作用の修正

Pillow 12 で `Image.getdata()` が非推奨になり警告が出ていたため、
`get_flattened_data()` があればそちらを使うフォールバックを selftest に入れた。

# 改善検証: B（ラベル・非PIIを壊さない）

## 実装

`protected_label_boxes()` を追加し、OCRの視覚行から既知のラベル文字列のbboxを求める。
エンティティ検出bboxがラベルbboxに20%以上重なる場合、その検出だけを捨てる。
値側の別bboxや `--mask-box` / `--mask-right-of` は維持する。

既定保護ラベルには `メール` `住所` `起票者` `開始日` `月額` `累計売上` `契約ID` などを含め、
画面固有の見出しは `--protected-label` で追加する。

## サポートチケット画像での回帰

新規に作成した920x700画像（チケット画面）に以下を配置した。

- 氏名・会社名・電話・メール・住所
- クレジットカード番号、マイナンバー形式、携帯番号
- Bearer/JWT、DB URI、内部IP

## 発見した実装バグ

`--protected-label` を指定した場合、初期実装は既定ラベルをカスタム指定で置き換えていた。
そのため `--protected-label サポートデスク` とすると `メール` の既定保護が無効になった。
カスタムラベルを既定リストへ追加する実装に修正し、既存セルフテストと新規画像で再確認した。

## 残る限界

- OCRがラベル自体を読まない場合、ラベル保護は発動しない
- OCRがラベルと値を同一bboxに結合した場合、そのbboxは保護されるため値の自動マスクを失う可能性がある
- その場合は `--mask-box` または `--mask-right-of` を明示指定する
- 再OCRの `leaks=[]` だけではラベル破損を検出できないため、dry-run目視とラベル保持テストを併用する
