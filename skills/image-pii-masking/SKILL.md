# 画像内PIIマスキング

画像の**文字**として写り込んだ機密情報を消す。ローカル完結、ネットワーク送信なし。

顔・ナンバープレートは対象外（`deface` / `EgoBlur` を使う）。DICOM は Presidio の
`DicomImageRedactorEngine` を使う。

## 中核となる立場

- **ぼかし・モザイクは使わない。** 不透明な単色で塗りつぶす。ぼかしは条件次第で推定余地が残る。
- **自動検出は必ず取りこぼす。** 検出0件は「安全」ではなく「未検証」として扱う。
- **1回のOCRでは領域が丸ごと落ちる。** 既定で複数のOCRパスを合成する。塗り足しは安全側なので合成する。
- **塗り過ぎは許容し、塗り漏れは許容しない。** ただし**ラベル（項目名）は塗らない**。
  ラベルが残れば何を伏せたかが伝わり、資料としての価値が残る。
- 既定のラベル保護に加え、画面固有のタイトル・見出しは `--protected-label` で追加する。
- **公開前に必ず `--dry-run` の目視レビューを挟む。** エージェントの判断だけで公開判定をしない。
- **検証を通ったことと、視覚的に隠れていることは別物。** 検証は再OCRの文字列比較なので、
  白背景に白塗りのような「読めないが見た目も変わらない」ケースは検証を通過する。

## 手順

### 1. 対象と要件を確定する

確認する項目：画像の言語（日本語混在か）、対象PII（氏名・住所・APIキー等）、出力の用途
（社内共有 / 公開 / LLM投入）、元画像を保持するか。公開用途なら人間の最終確認を必須にする。

### 0. 環境が信用できるか確かめる（初回・依存更新後）

```bash
uv run scripts/selftest.py
```

合成画像でワークフロー全体を回し、34項目を検査する（約13秒）。
検査内容：PII領域のインク画素が全て塗り潰されたか、ラベルと非PIIのインクが
1画素も改変されていないか、終了コード 0/2/3 の契約、検証器自体の健全性、EXIF非残留。
**Tesseract・Presidio・spaCy を更新したら必ず再実行する。** OCRの挙動は版で変わる。

### 2. 環境を確認する

**Python依存は uv で隔離済み。事前の `pip install` も venv 有効化も不要。**
両スクリプトは PEP 723 インラインメタデータで依存とバージョンを固定しており、
`uv run` が使い捨ての環境に解決する。常に `uv run` で呼ぶ。

```bash
uv run scripts/mask_image.py ...    # 推奨
./scripts/mask_image.py ...         # shebang 経由でも同じ（uv run --script）
```

固定している依存: presidio-image-redactor 0.0.60 / presidio-analyzer 2.2.364 /
pillow >=10,<14 / spacy >=3.8,<3.9 / ja_core_news_sm 3.8.0、Python >=3.10,<3.13。
`ja_core_news_sm` は日本語の氏名・地名検出（NER）に使う。英語画像のみなら
`--language en` に切り替え、メタデータの model を `en_core_web_sm` に差し替える。

**隔離されないもの: Tesseract 本体。** これはシステムバイナリなので uv の管理外。
実行前に必ず確認する。

```bash
tesseract --list-langs | grep -E '^(jpn|eng)$'   # 日本語モデルの有無
```

無ければ導入する（macOS）:

```bash
brew install tesseract tesseract-lang
```

OCR結果はTesseractの版とtraineddataで変わる。**Tesseractを更新したらステップ0を再実行する。**

### 3. 候補を目視レビューする（必須）

```bash
uv run scripts/mask_image.py IN.png -o preview.png --dry-run --report report.json
```

赤枠が候補領域。`report.json` の `detections` で検出文字列・スコアを確認し、
**枠が付いていない機密情報**を探す。取りこぼしがあれば、原因ごとに手を打つ：

| 症状 | 原因 | 対処 |
|---|---|---|
| 特定の行だけ枠が無い | その行のOCRが失敗 | `report.json` の `ocr_passes` を見る。`--ocr-pass 3:2 --ocr-pass 6:1 --ocr-pass 11:2` を追加 |
| 氏名・社名が拾われない | NERの取りこぼし | `--deny-list-file names.txt`（既知の固有名詞を列挙） |
| 独自形式のID・トークン | パターン未定義 | `--extra-pattern EMP_ID=EMP-\d{6}` |
| 全体的に感度不足 | しきい値 | `--threshold 0.2` |
| OCRが単語を分割して一致しない | 例: `タナカ`→`タナ カ` | `--mask-box X,Y,W,H` で領域を直接指定 |
| 誤検出で消したくない語がある | 過検出 | `--allow-list 更新 CT-2024-000871` |
| 特定項目の値だけ確実に消したい | エンティティ検出では粗すぎる | `--mask-right-of '生年月日:220'` |

`--mask-box` は検出結果に依存せず必ず塗る。**OCRが読めない領域の最終手段はこれ。**

### ラベル保護

既定で以下のような項目名を保護する：`氏名` `住所` `電話番号` `メール` `起票者`
`契約状態` `開始日` `月額` `累計売上` `契約ID` など。検出ボックスがラベルに
20%以上重なる場合は、そのボックスを捨てる。値側の別ボックスは引き続き処理する。

画面タイトルや固有の見出しは追加指定する。

```bash
--protected-label 'サポートデスク' --protected-label '顧客情報'
```

これは既定ラベルへの追加であり、既定値を置き換えない。OCR がラベル自体を認識できない、
または値と同じボックスに結合される場合は、値領域を `--mask-box` で指定する。
手書き、装飾フォント、極端な低解像度は原理的にここに落ちる。

### ラベル／値レイアウトでは `--mask-right-of` を使う

帳票・CRM画面のような「項目名: 値」形式で、特定項目を確実に消したい場合は
エンティティ検出を強めるのではなく、ラベルをアンカーにして値セルを塗る。

```bash
--mask-right-of '生年月日:220'   # ラベルの右端から220pxを塗る
```

**注意: 行グループは左右のカードを同一行として連結する。**
実測では `'生年月日1985年4月12日開始日2024年10月1日'` という1行になった。
幅を大きくとりすぎると隣のカラムまで塗るので、dry-run で幅を調整する。

`DATE_TIME` を有効にして生年月日を消そうとするのは失敗する。実測ではラベル文字
`生年月日` の `年月日` 自体と、非PIIの `開始日: 2024年10月1日`、`契約状態` の一部まで
塗ってしまった。このため `DATE_TIME` は既定エンティティから除外してある。

### 4. 塗りつぶす

```bash
uv run scripts/mask_image.py IN.png -o masked.png --report report.json --pad 4 \
  --deny-list-file names.txt \
  --mask-right-of '生年月日:220' \
  --allow-list 更新 CT-2024-000871
```

既定のOCRパスは `3:2`（自動レイアウト解析・2倍拡大）と `6:1`（単一ブロック・原寸）の合成。
`PSM:UPSCALE` 形式で `--ocr-pass` を追加できる。

出力は常に PNG。EXIF / GPS は保存時に落ちる（JPEG入力でも出力側にメタデータは残らない）。
元画像を残す場合は、元画像側の共有経路を絶対に開かない。

### 5. 終了コードで判定する

| コード | 意味 | 対応 |
|---|---|---|
| 0 | 検出あり・再OCRで残存なし | 目視確認へ進む |
| 2 | 検出した文字列が masked 画像から再度読めた | 公開しない。`--pad` を増やす、`--psm` を変える |
| 3 | 検出0件かつ手動box0件 | 「安全」と扱わない。OCRが機能しているか（`report.json` の `ocr_passes[].ocr_text_length`）を確認 |

`ocr_text_length` が0に近い場合は OCR 自体が失敗している。`--lang`、解像度、
`--ocr-pass 11:2`（疎なテキスト向け）を見直す。

### 6. 残存リスクを申し送る

成果物と一緒に、`report.json` のパス、目視レビューの実施有無、取りこぼし可能性のある
領域（低解像度部分、装飾フォント、図中の文字）を明記する。

## 請求書・金融情報を消す（`financial` プロファイル）

請求書・契約サマリ・支払情報では、会社名、金額、口座番号も機密になり得る。
これらは通常のPIIとは限らないため、既定では消さず、明示的にプロファイルを選ぶ。

```bash
uv run scripts/mask_image.py invoice.png -o masked.png --report report.json \
  --profile financial
```

`financial` は以下を追加する：

- `JP_MONEY`: `120,000 円`、`80.000 円` などの金額
- `BANK_ACCOUNT`: 7〜8桁の口座番号形式
- `請求先` の値セル
- `振込先` の値セル

ラベル自体（`請求先`、`振込先`、`月額`、`合計`）は保護する。
口座番号の前後にある銀行名など、支払先情報全体も値セルとしてマスクする設計。

**既定の `standard` プロファイルでは金融情報を消さない。**

## PII 以外の機密値を消す（金額・取引先名・契約条件など）

**コード変更なしで対応できる。** 金額や社内固有の数値は一般的な PII ではないため
既定では消さないが、次の2経路で追加できる。

### 推奨: 正規表現を追加する

```bash
--extra-pattern 'JP_MONEY=[0-9][0-9,\. ]{2,}\s?円'
```

実測で `480,000 円` と `5,760,000 円` を捕捉し、ラベル『月額』『累計売上』と
他の非PII（プラン、契約状態、開始日、更新区分、契約ID）は改変画素0で保持された。
桁区切りを `.` と誤読しても拾えるよう文字クラスに `.` を入れてある。

### 代替: ラベル基準で指定する

```bash
--mask-right-of '月額:240' --mask-right-of '売上:230'
```

金額の書式が不定で正規表現が組みにくい場合に使う。ただしラベルのOCR誤読で外れる。
実測で `累計売上` が `索計売上` と読まれ、`--mask-right-of '累計売上'` は不発だった。
**ラベルは短い部分文字列（`売上`）で指定する方が強い。**

### 効かない経路

`--entities ... MONEY` は不発だった。`ja_core_news_sm` が `480,000 円` を
`MONEY` としてタグ付けしないため。NER に期待せずパターンで解く。

### 同じ要領で他の値も消せる

| 消したいもの | 指定例 |
|---|---|
| 取引先名・自社名 | `--deny-list-file companies.txt` |
| 契約ID・会員番号 | `--extra-pattern 'CONTRACT_ID=CT-\d{4}-\d{6}'` |
| 次期施策など自由記述欄 | `--mask-right-of '備考:400'` |
| グラフ・画像領域 | `--mask-box X,Y,W,H`（OCR対象外なのでこれしかない） |

いずれも dry-run → 目視レビュー → 塗りつぶし → 検証の手順は変わらない。

## 検出対象（既定）

Presidio 既定: `PERSON` `LOCATION` `EMAIL_ADDRESS` `CREDIT_CARD` `IBAN_CODE`
`IP_ADDRESS` `CRYPTO`

日本語・秘密情報向け追加パターン: `JP_PHONE` `JP_POSTAL_CODE` `JP_MYNUMBER`
`JP_ADDRESS` `EMAIL_LOOSE` `SECRET_TOKEN`（AWSキー / GitHubトークン / `sk-` 形式 /
Slackトークン / Bearer / JWT / PEM秘密鍵ヘッダ）

正規表現は OCR が挿入する空白と誤読を前提に緩めてある。詳細と実測挙動は
`references/measured-behavior.md` を参照。

## 確認済みの限界

`references/measured-behavior.md` にテスト画像での実測結果を記録している。要点：

- **単一OCRパスは行を丸ごと落とす。**
- **新しいレイアウトではラベル保護が必須。** サポートチケット画像で、電話番号の誤検出
  ボックスが `メール` ラベルへ誤マッピングされる事例を確認した。既定ラベル保護で改変0にした。
  画面タイトル `サポートデスク` はカスタム `--protected-label` が必要だった。 実測で、暗背景・等幅の長いURL行（Slackトークンを含む）が
  `--psm 6` の全画面OCRで完全に読まれなかった。切り出すと読めるため検出漏れに気付きにくい
- **PSMを変えると別の検出が壊れる。** `psm 3` は落ちた行を救う一方、読み取り順が変わり
  `sk-`／`AKIA` の検出を落とした。だから既定で複数パスを合成している
- OCR 誤読はそのまま検出漏れになる（例: `example.co.jp` → `example.coJjp` で厳密な
  メール正規表現は不発。`EMAIL_LOOSE` で救済しているが、原理的に完全ではない）
- OCRの単語分割により、deny-list の文字列一致が効かないことがある（`タナカ` → `タナ カ`）。
  `--mask-box` でしか潰せない
- NER は日本語の氏名を落とす。ラベル付きフィールド（`担当営業: 鈴木 花子`）でも落ちた実測あり
- **`DATE_TIME` はラベルを壊すので既定から除外した。** 日付を消すなら `--mask-right-of` を使う
- 住所パターンは貪欲に隣接テキストを巻き込む（安全側の誤りだが、必要な情報も消える）
- `LOCATION` は数字列を誤検出する（契約ID `CT-2024-000871` の `000871` を地名と判定した）。
  `--allow-list` で戻す
- マイナンバー相当の12桁パターンは注文番号等と衝突しやすい
- 手書き、極端な低解像度、装飾フォントは OCR が拾えず検出できない
